### 📘 0427 · Mon

#### 오늘 한 일 (What I did)

- 러닝 앱의 주요 화면 흐름을 기준으로 화면 설계를 구체화했다.
- 코스 목록, 러닝 기록, 코스 상세 등 사용자가 자주 접근할 화면의 구성 요소를 정리했다.
- 러닝 앱의 서비스 방향에 맞춰 디자인 컨셉과 기본 UI 톤을 고민했다.

---

#### 배운 것 (What I learned)

- 화면 설계는 단순히 예쁘게 배치하는 것이 아니라, 사용자가 어떤 순서로 기능을 사용할지 함께 고려해야 한다는 것을 배웠다.
- 모바일 화면에서는 검색, 필터, 정렬, 페이지네이션 같은 기능을 한 화면에 과하게 넣지 않도록 우선순위를 정하는 것이 중요하다는 것을 알게 되었다.
- 러닝 앱에서는 지도, 기록 카드, 거리/페이스 정보처럼 사용자가 바로 이해할 수 있는 정보 구조가 중요하다는 것을 배웠다.

---

#### 문제 & 해결 (Problem & Solution)

- 코스 목록 화면에 검색, 필터, 정렬, 페이지네이션 요소를 어떻게 배치할지 고민했고, 카드형 목록 중심으로 구성하는 방향을 잡았다.
- 화면별 기능이 많아져 복잡해질 수 있어, 우선 핵심 정보가 잘 보이도록 화면 구조를 단순화했다.
- 서비스의 분위기가 명확하지 않아 러닝 앱과 코스 드로잉 기능에 어울리는 디자인 컨셉과 컬러 방향을 정리했다.

---

#### 느낀 점 (Insight)

- 화면 설계를 구체화하다 보니 실제 개발에서 필요한 데이터와 API가 더 명확하게 보이기 시작했다.
- UI를 먼저 그려보는 과정이 백엔드 데이터 구조를 고민하는 데도 도움이 된다고 느꼈다.
- 좋은 화면 설계는 기능을 많이 넣는 것보다 사용자가 자연스럽게 이해하고 사용할 수 있게 만드는 것이라고 생각했다.

---

#### 내일 할 것 (Next)

### 📘 0428 · Tue

#### 오늘 한 일 (What I did)

- 앱 화면 설계를 진행하며 주요 화면 흐름과 필요한 기능을 정리했다.
- 화면을 너무 세부적으로 완성하기보다, 직접 구현하면서 조정하는 방향이 더 적절하다고 판단했다.
- 백엔드 코드 설계를 시작하고, 러닝 종료 기록 저장 API의 구조를 잡기 시작했다.

---

#### 배운 것 (What I learned)

- 화면 설계는 디테일을 끝까지 고정하기보다, 구현 가능성과 데이터 흐름을 함께 고려해야 한다는 것을 배웠다.
- 러닝 종료 시 FE에서 nodes, 거리, 시간 등의 데이터를 전달하고 BE에서 기록으로 저장하는 흐름을 이해했다.
- `tracks`와 `records`의 역할을 나누어 경로 데이터와 러닝 기록 데이터를 분리하는 방식이 필요하다는 것을 알게 되었다.

---

#### 문제 & 해결 (Problem & Solution)

- 화면 설계가 너무 디테일해지면서 실제 구현과 맞지 않을 가능성이 있어, 우선 핵심 기능 구현을 병행하기로 했다.
- 러닝 종료 기록 API에서 어떤 데이터를 FE가 보내고, 어떤 데이터를 BE가 저장할지 고민했고 nodes, 거리, 시간, 이미지 URL 등을 기준으로 정리했다.
- 경로 데이터와 기록 데이터를 한 테이블에 모두 넣기보다 `Track`과 `RunningRecord`로 분리하는 방향으로 설계했다.

---

#### 느낀 점 (Insight)

- 기획과 화면 설계도 중요하지만, 실제 구현을 시작해야 더 현실적인 구조가 보인다는 것을 느꼈다.
- API를 설계할 때는 단순히 요청/응답만 보는 것이 아니라 DB 테이블과 도메인 책임까지 함께 봐야 한다고 느꼈다.
- 처음부터 완벽하게 설계하려 하기보다, 구현하면서 점진적으로 다듬는 방식이 더 효율적일 수 있다고 생각했다.

---

#### 내일 할 것 (Next)

- FE에서 받은 nodes를 `MultiLineString`으로 변환하는 로직을 구현하기.
- 기록 저장 API의 DTO, Converter, Service, Controller를 순서대로 작성하기.

### 📘 0429 · Wed

#### 오늘 한 일 (What I did)

- 러닝 종료 시 FE에서 전달한 nodes 데이터를 `MultiLineString`으로 변환해 `tracks` 테이블에 저장하는 흐름을 구현했다.
- `Track`, `RunningRecord` 엔티티와 Repository, Service, Converter, Controller 구조를 작성했다.
- 러닝 기록 전체 조회 API와 상세 조회 API를 구현하고 Swagger로 동작을 확인했다.

---

#### 배운 것 (What I learned)

- PostGIS의 `geometry(MultiLineString, 4326)`에서 SRID 4326은 GPS 위도/경도 좌표계라는 것을 배웠다.
- JTS의 `Coordinate`, `LineString`, `MultiLineString`, `GeometryFactory`를 이용해 Java에서 공간 데이터를 다루는 방법을 알게 되었다.
- `@ManyToOne(fetch = FetchType.LAZY)`를 통해 `records.track_id`를 `Track` 객체로 매핑하고, 필요한 시점에 조회하는 방식을 이해했다.

---

#### 문제 & 해결 (Problem & Solution)

- 프론트의 좌표는 `lat, lng` 순서지만 JTS/PostGIS에서는 `lng, lat` 순서로 넣어야 해서 변환 시 좌표 순서를 주의해서 처리했다.
- `MultiLineString`에서 `getGeometries()`를 사용할 수 없어 `getNumGeometries()`와 `getGeometryN()` 방식으로 내부 좌표를 꺼내도록 수정했다.
- 목록 조회는 무한스크롤을 고려해 `Page` 대신 `Slice` 기반으로 구성하고, `hasNext`를 응답하도록 설계했다.

---

#### 느낀 점 (Insight)

- 지도 경로 데이터는 단순 문자열이나 배열이 아니라 좌표계, 저장 타입, 변환 순서까지 함께 고려해야 한다는 것을 느꼈다.
- Entity, DTO, Converter, Service의 책임을 분리하면 코드 흐름이 더 길어지더라도 구조를 이해하기 쉬워진다는 것을 알게 되었다.
- 기록 목록과 상세 조회는 필요한 데이터 범위가 다르기 때문에 응답 DTO를 분리하는 것이 중요하다고 느꼈다.

---

- 사용자 활동 통계 조회 API 구현

### 📘 0430 · Thu

#### 오늘 한 일 (What I did)

- 러닝 기록 제목 수정 API 구현
- 사용자 활동 통계 조회 API 구조 설계

---

#### 배운 것 (What I learned)

- 통계 조회처럼 반복적으로 계산되는 데이터는 별도 통계 테이블을 통해 조회 성능 개선할 수 있음
- postgreSQL에서 사용할 수 잇는 upsert 처리에 대해서 공부
    - insert + update 로 row가 없으면 생성하고, 있으면 누적 업데이트 하는 쿼리


---

#### 문제 & 해결 (Problem & Solution)

- 통계를 매번 records에서 계산하면 조회 비용이 커질 수 있어 member_record_stats 테이블을 추가하는 방식으로 변경했다.
- 통계 row 최초 생성 시 동시 요청이 들어오면 Unique Constraint 충돌이 발생할 수 있어 upsert 방식 도입을 검토했다.
- 잘못된 period 값이 들어왔을 때 단순 BAD_REQUEST만 반환하던 문제를 전용 에러와 잘못된 입력값을 포함하는 방식으로 개선하기로 했다.

---

#### 느낀 점 (Insight)

- 단순히 기능이 동작하는 것보다, 데이터가 쌓였을 때의 조회 성능과 동시성까지 고려하는 것이 중요하다고 느꼈다.
- 통계 기능은 조회 API만 보는 것이 아니라, 기록 생성 시점의 데이터 누적 흐름까지 함께 설계해야 한다는 점을 알게 되었다.
- Converter, Service, Entity의 책임을 분리하는 컨벤션을 지키는 것이 코드 구조를 훨씬 명확하게 만든다고 느꼈다.
