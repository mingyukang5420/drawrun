### 📘 0504 · Mon

#### 오늘 한 일 (What I did)

- EC2 서버 안의 PostgreSQL/PostGIS 컨테이너를 확인하고, DBeaver에서 외부 접속할 수 있도록 DB 연결 정보를 확인했다.
- 러닝 기록, 코스, 트랙, 지역, 활동 통계 테스트를 위한 더미 데이터 SQL을 작성하고 삽입 흐름을 점검했다.
- 더미 데이터 삽입 후 members, tracks, districts, courses, records 등의 시퀀스를 setval(pg_get_serial_sequence(...))로 재정렬하는 방법을 정리했다.

---

#### 배운 것 (What I learned)

- Docker 컨테이너가 0.0.0.0:5432->5432로 포트 매핑되어 있으면 외부 DB 클라이언트에서 해당 서버 IP와 포트로 접근할 수 있다는 것을 배웠다.
- DB에 해시 처리된 비밀번호가 저장되어 있어도 로그인이나 DB 접속 시에는 해시 전 원문 비밀번호를 사용해야 한다는 점을 이해했다.
- 더미 데이터를 직접 넣은 뒤에는 auto increment 시퀀스가 꼬일 수 있으므로, 현재 테이블의 최대 ID 기준으로 시퀀스를 맞춰야 한다는 것을 배웠다.

---

#### 문제 & 해결 (Problem & Solution)

- 문제: DBeaver에서 EC2 내부 PostgreSQL에 접속하기 위해 Host, Port, Database, 계정 정보를 어떻게 확인해야 하는지 헷갈렸다.
해결: EC2에 SSH 접속한 뒤 Docker 컨테이너 상태와 포트 매핑을 확인하고, 해당 정보를 바탕으로 DBeaver 연결을 구성했다.
- 문제: 더미 데이터를 수동 삽입하면 이후 자동 생성 ID가 기존 ID와 충돌할 수 있었다.
해결: setval(pg_get_serial_sequence(...), COALESCE((SELECT MAX(id) ...), 1)) 방식으로 각 테이블의 시퀀스를 현재 최대 ID에 맞췄다.
- 문제: 활동 통계 데이터는 단순히 records에만 넣는 것이 아니라 member_record_stats에도 반영되어야 했다.
해결: 러닝 기록 더미 데이터와 함께 통계 테이블에 들어갈 누적 거리, 횟수, 시간, 평균 페이스 데이터를 별도로 구성했다.

---

#### 느낀 점 (Insight)

- 백엔드 API를 테스트하려면 코드 구현뿐 아니라 DB 더미 데이터, 시퀀스, 외부 접속 환경까지 함께 준비되어야 한다는 걸 느꼈다.
- 실제 서버 DB에 연결해보니 로컬 개발 환경과 운영/배포 환경의 차이를 더 명확히 이해할 수 있었다.
- ERD를 기준으로 더미 데이터를 넣어보니 테이블 간 관계와 외래키 흐름을 더 구체적으로 파악할 수 있었다.

---

- Swagger 또는 DBeaver를 통해 기록/코스 관련 조회 API 응답이 기대한 형태로 나오는지 확인하기

### 📘 0506 · Wed

#### 오늘 한 일 (What I did)

- 기존 ERD 구조를 다시 검토하고, 하나의 `course` 테이블로 공식 코스와 에디터 코스를 함께 관리하던 방식을 재정리했다.
- 재사용성을 높이려던 초기 설계가 오히려 분기와 예외 처리를 많이 만들고 있어서, `코스`와 `에디터 코스` 테이블을 분리하는 방향으로 구조를 수정했다.
- 팀원들과 ERD 변경 방향을 다시 맞추면서, 이후 백엔드 로직 흐름이 더 단순해지도록 기준을 정리했다.

---

#### 배운 것 (What I learned)

- 재사용성을 높인 설계가 항상 좋은 것은 아니고, 도메인 성격이 다른 데이터를 억지로 하나로 합치면 오히려 복잡도가 커질 수 있다.
- ERD는 테이블 수를 줄이는 것보다, 실제 비즈니스 흐름이 자연스럽게 읽히는지가 더 중요하다는 걸 느꼈다.
- 설계 단계에서 팀원들과 해석 차이를 빨리 맞추는 것이 이후 구현 비용을 줄이는 데 큰 도움이 된다.

---

#### 문제 & 해결 (Problem & Solution)

- 기존에는 공식 코스와 에디터 코스를 하나의 `course` 테이블로 관리해서 분기점이 많아지고 코드 복잡도가 커졌다.
  - `코스`와 `에디터 코스`를 분리하는 방향으로 ERD를 수정해 흐름을 더 명확하게 정리했다.
- 팀원마다 구조를 바라보는 관점이 조금씩 달라 설계 해석 차이가 있었다.
  - 테이블 역할을 다시 정의하면서 공통 이해를 맞추고, 이후 구현 방향도 더 수월하게 정리할 수 있었다.

---

#### 느낀 점 (Insight)

- 깔끔해 보이는 설계보다, 실제 구현과 협업에서 덜 헷갈리는 설계가 더 좋은 설계라는 걸 느꼈다.
- ERD를 정리하는 과정 자체가 단순한 테이블 수정이 아니라, 팀의 사고방식을 맞추는 과정이라는 생각이 들었다.

### 📘 0508 · Fri

#### 오늘 한 일 (What I did)

- `run/start` API 흐름을 다시 정리하고, 자유 러닝 / 공식 코스 / 에디터 코스 분기 기준을 명확히 했다.
- `RunRequest`, `RunResponse`, `RunConverter`, `RunService`, `RunController`를 작성해 `run` 도메인 기본 구조를 잡았다.
- 요청 테스트와 로그 확인을 통해 실제로 어떤 값이 들어오는지 점검했다.

---

#### 배운 것 (What I learned)

- 시작 API는 별도 entity 없이도 `controller - service - converter - dto` 구조로 충분히 설계할 수 있다.
- `null`로 온다고 생각한 값도 실제로는 `0`으로 들어올 수 있어서, 요청값을 직접 확인하는 과정이 중요하다.
- 서비스는 분기와 조회, converter는 응답 변환 역할로 나누는 게 깔끔하다.

---

#### 문제 & 해결 (Problem & Solution)

- 자유 러닝 요청에서 `courseId`, `courseDraftId`가 `null`이 아니라 `0`으로 들어와 `BAD_REQUEST`가 발생했다.
  - 로그를 추가해 실제 요청값을 확인하고 원인을 파악했다.
- `courseDraftId` 요청 시 500 에러가 발생했는데, 원인은 `course_drafts` 테이블과 엔티티 스키마 불일치였다.
  - 코드 문제가 아니라 DB 컬럼 누락 문제라는 점을 확인했다.

---

#### 느낀 점 (Insight)

- 코드를 빨리 짜는 것보다 API 의도를 먼저 정확히 이해하는 게 더 중요하다는 걸 느꼈다.
- 오늘은 특히 “내가 예상한 값”보다 “실제로 들어온 값”을 확인하는 습관이 중요했다.
