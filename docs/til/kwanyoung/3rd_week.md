### 📘 0421 · Tue

#### 오늘 한 일 (What I did)

- 서비스 플로우 회의
- 사용자 경험 기준으로 화면 흐름 및 기능 흐름 정리
- 팀원들과 각자 생각한 서비스 진행 방식 싱크 맞추기

---

#### 배운 것 (What I learned)

- 같은 기능을 이야기하더라도 각자가 떠올리는 사용자 흐름은 생각보다 다를 수 있다
- 서비스 플로우를 맞추려면 기능 단위보다 사용자의 행동 순서 기준으로 이야기하는 것이 더 명확하다
- 초기에 팀원 간 이해를 맞춰두는 과정이 이후 기획과 개발 방향을 흔들리지 않게 해준다

---

#### 문제 & 해결 (Problem & Solution)

- 팀원마다 생각하는 서비스 흐름이 달라 기능 연결 방식에 차이가 있었음 → 사용자 입장에서 시작부터 종료까지의 흐름을 함께 정리하며 싱크를 맞춤
- 기능 중심으로 이야기하다 보니 전체 경험이 잘 보이지 않았음 → 사용자가 어떤 상황에서 어떤 행동을 하는지 기준으로 플로우를 다시 정리
- 세부 화면 전환이나 기능 위치에 대한 의견 차이가 있었음 → 우선 핵심 흐름을 먼저 정하고 세부 기능은 이후 구체화하기로 함

---

#### 느낀 점 (Insight)

- 서비스 기획에서는 좋은 아이디어보다 팀원들이 같은 그림을 보고 있는지가 더 중요하다고 느꼈다
- 머릿속으로는 당연하다고 생각한 흐름도 말로 풀어보면 서로 다르게 이해하고 있을 수 있다는 걸 알게 됐다
- 사용자 경험을 기준으로 이야기하니 기능의 필요성과 위치가 더 자연스럽게 정리되는 것 같았다

---

#### 내일 할 것 (Next)

- 서비스 플로우 기반 기능 구체화
- 주요 화면 구성 정리
- 기획 문서에 서비스 흐름 반영

---

### 📘 0422 · Wed

#### 오늘 한 일 (What I did)

- 어제 회의 내용을 바탕으로 기능명세서 작성
- ERD와 API 명세서 작업 분담
- ERD 작성 참여

---

#### 배운 것 (What I learned)

- 서비스 플로우를 기능명세서로 옮기면 필요한 기능과 데이터가 더 구체적으로 보인다
- ERD를 작성하려면 단순히 테이블을 나누는 것보다 기능 흐름과 데이터 관계를 함께 생각해야 한다
- 명세서를 나눠서 작성하더라도 서로 연결되는 부분이 많아 팀원 간 기준을 맞추는 것이 중요하다

---

#### 문제 & 해결 (Problem & Solution)

- 기능명세서를 작성하면서 필요한 데이터 구조가 아직 명확하지 않은 부분이 있었음 → ERD를 작성하며 필요한 테이블과 관계를 하나씩 정리
- ERD와 API 명세서가 서로 맞물리는 부분이 있어 작업 기준이 흔들릴 수 있었음 → 역할을 나누되 추후 다시 맞춰보기로 함
- ERD를 완성하지 못했음 → 내일 이어서 마무리하기로 계획

---

#### 느낀 점 (Insight)

- 기획 단계에서 정리한 내용이 실제 명세서로 옮겨지면 부족한 부분이 더 잘 드러나는 것 같다
- ERD는 단순한 DB 구조가 아니라 서비스가 어떻게 동작할지 보여주는 설계도에 가깝다고 느꼈다
- 처음부터 완벽하게 작성하기보다는 계속 수정하면서 맞춰가는 과정이 중요하다고 생각했다

---

#### 내일 할 것 (Next)

- ERD 작성 마무리
- API 명세서와 데이터 구조 연결 확인
- 기능명세서에서 빠진 부분 점검

---

### 📘 0423 · Thu

#### 오늘 한 일 (What I did)

- ERD 작성 이어서 진행
- 테이블 분리 여부와 데이터 구조에 대해 팀원들과 논의
- 서비스 플로우에 맞는 데이터 설계 방식 검토

---

#### 배운 것 (What I learned)

- 같은 데이터를 다루더라도 테이블을 어떻게 나누느냐에 따라 서비스 구현 방식이 달라질 수 있다
- ERD 설계에서는 정답 하나를 찾기보다 서비스 흐름에 더 적합한 구조를 선택하는 과정이 중요하다
- 데이터 구조를 정할 때는 저장 편의성뿐만 아니라 조회, 확장성, 유지보수까지 함께 고려해야 한다

---

#### 문제 & 해결 (Problem & Solution)

- 테이블을 분리할지 하나로 둘지에 대한 의견이 나뉘었음 → 우리 서비스의 데이터 흐름과 사용 방식을 기준으로 비교하며 논의
- 설계 방식마다 장단점이 있어 결정에 시간이 오래 걸렸음 → 각 방식이 서비스 플로우에 어떤 영향을 주는지 따져보며 선택
- ERD 작성 과정에서 놓칠 수 있는 관계들이 있었음 → 팀원들과 의견을 나누며 더 적절한 구조로 수정

---

#### 느낀 점 (Insight)

- ERD는 단순히 테이블을 그리는 작업이 아니라 서비스 전체 구조를 데이터 관점에서 검증하는 과정이라고 느꼈다
- 여러 의견을 나누다 보니 혼자 생각했을 때보다 더 나은 설계 방향을 찾을 수 있었다
- 시간이 오래 걸리더라도 이유를 가지고 선택하는 과정이 중요하다고 생각했다

---

#### 내일 할 것 (Next)

- ERD 세부 관계 점검
- API 명세서와 ERD 연결 확인
- 기능명세서와 데이터 구조 불일치 여부 확인

### 📘 0424 · Fri

#### 오늘 한 일 (What I did)

- ERD 작성 마무리
- 컨설턴트님과 팀 미팅 진행
- 피그마를 활용한 화면 설계 일부 진행

---

#### 배운 것 (What I learned)

- 외부 피드백을 통해 서비스의 핵심 방향을 다시 점검할 수 있다
- 기능을 많이 넣는 것보다 서비스의 차별점이 잘 드러나는 요소에 집중하는 것이 중요하다
- 화면 설계를 시작하면 기획한 기능이 실제 사용자 흐름에서 어떻게 보일지 더 구체적으로 확인할 수 있다

---

#### 문제 & 해결 (Problem & Solution)

- 기존에는 게이미피케이션 요소와 드로잉 요소가 함께 있어 서비스의 핵심이 다소 분산될 수 있었음 → 컨설턴트님 의견을 바탕으로 드로잉 요소에 더 집중하기로 결정
- 서비스 방향성이 일부 변경되면서 기존 기획과 ERD에 영향을 줄 수 있었음 → 변경된 방향에 맞춰 필요한 부분을 다시 점검하기로 함
- 화면 설계가 아직 구체화되지 않은 부분이 있었음 → 피그마로 주요 화면을 조금씩 구성하며 흐름을 확인

---

#### 느낀 점 (Insight)

- 좋은 서비스는 많은 기능보다 명확한 핵심 경험을 중심으로 설계되어야 한다고 느꼈다
- 피드백을 받아 방향을 수정하는 과정도 기획에서 중요한 단계라는 것을 알게 됐다
- 화면으로 직접 그려보니 머릿속에 있던 서비스 흐름이 더 현실적으로 다가왔다
