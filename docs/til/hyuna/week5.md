### 📘 0506 · Wed

#### 오늘 한 일 (What I did)

- 코스 에디터 도로 데이터 로드 기능 구현
- 도로 데이터를 화면에 표시하는 작업 진행
- 코스 저장 기능 구현
- API 응답 데이터 중 화면에 표시되지 않는 문제 원인 확인

---

#### 문제 & 해결 (Problem & Solution)

- 문제
  - 도로 데이터를 불러왔지만 화면에 정상적으로 표시되지 않음
  - 응답 데이터 중 일부 name 필드가 null로 내려오면서 화면 렌더링 과정에서 문제가 발생함

- 원인
  - 화면에서 확인한 응답 외에도 추가 데이터가 함께 내려오고 있었음
  - 해당 데이터의 name 값이 null인 경우를 고려하지 않음
  - 타입 정의와 실제 응답 데이터 간 차이를 충분히 확인하지 못함

- 해결
  - CLI로 데이터 구조를 확인했지만 원인 파악에 시간이 지체되어 팀장님에게 도움을 요청
  - null 가능성을 고려하여 optional 처리 추가
  - name 필드 접근 시 ? 처리를 추가하여 화면 렌더링 문제 해결

---

- 코스 에디터 기능 안정화
- 도로 데이터 렌더링 예외 케이스 추가 확인

### 📘 0508 · Fri

#### 오늘 한 일 (What I did)

- 서비스 방향성에 맞춰 화면 구조 재설계
- 사용자 입장에서 왜 이 서비스를 사용할지에 대한 흐름 재검토
- 추후 추가될 기능을 고려하여 네비게이션 바 구조 수정
- 날씨 기능 연동을 위해 백엔드 API 요청 사항 정리
- Planning In Context 방식에서 발생하는 작업 속도 저하 원인 정리
- 작업 아웃풋 효율 개선을 위한 SDD 방식 도입 논의

---

#### 배운 것 (What I learned)

- UI/UX는 단순 화면 디자인이 아니라 서비스 설득 구조와 연결된다
- AI가 충분히 처리 가능한 작업에 과도한 시간을 사용하는 것은 전체 생산성을 낮출 수 있다

---

#### 문제 & 해결 (Problem & Solution)

- 문제
  - 팀 내 논의가 화면 흐름이나 기능 메리트보다 데이터 성능 개선 중심으로 치우침
  - 실제 사용자 경험보다 내부 구조와 최적화에 더 많은 시간이 사용됨
  - Planning In Context 방식으로 하나하나 세부적으로 고민하다 보니 작업 속도가 느려짐

- 원인
  - 완성도 높은 구조를 먼저 만들려고 하는 경향
  - 실제 서비스 검증보다 기술적 완성도를 우선시함
  - AI가 처리 가능한 반복 작업까지 직접 처리하려고 함

- 해결
  - 빠른 기능 검증과 화면 아웃풋 중심으로 우선순위 재정리
  - SDD 방식 도입을 통해 기능 정의 → 화면 흐름 → 구현 순으로 작업 구조 변경
  - AI를 단순 코드 생성이 아닌 생산성 향상 도구로 활용하는 방향으로 팀 기준 정리
  - 데이터 최적화보다 사용자가 체감하는 기능 흐름을 우선적으로 논의

---

#### 생각 흐름 (Insight)

- 지금 단계에서 중요한 것은 완벽한 구조보다 빠르게 사용 가능한 형태를 만드는 것이라고 느꼈다.
- 기술적인 완성도와 데이터 최적화도 중요하지만, 결국 서비스는 "사용자가 왜 이 서비스를 써야 하는가"에 대한 이유가 더 명확해야 한다고 생각했다.
- 최근 IT 서비스들은 완벽한 구현 이후 공개하는 방식보다, 빠르게 만들고 검증하며 개선하는 흐름으로 움직이고 있다는 점을 체감했다.
- 이 과정에서 개발의 중심이 단순 구현보다 설계와 검증으로 이동하고 있다는 생각이 들었고, DLC, TDD, SDD 방식에 대해 고민해보게 되었다.
- 항상 부족한 구현 능력이 성장의 발목을 잡는다고 생각했지만, 이제는 "어떻게 구현할까(How)"보다 "무엇을 만들 것인가(What)"를 먼저 명확히 정의하는 것이 더 중요하다고 느꼈다.
- 앞으로는 기능과 흐름을 MD 문서 기반으로 먼저 정의(SDD)하고, AI를 활용해 구현한 코드를 테스트(TDD)하며 검증하는 방향에 익숙해지는 것을 목표로 해보려 한다.
