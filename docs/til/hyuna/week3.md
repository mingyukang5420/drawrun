### 📘 0420 · Mon

#### 오늘 한 일 (What I did)

- 주말에 생각해온 기획을 기반으로 팀 미팅 진행
- 기존 기획을 재검토하고 새로운 기획 주제로 변경
- 서비스 도메인 확정
- 최종 기획 방향(GPS drawing)에 맞는 기획서 작성

---

#### 배운 것 (What I learned)

- 팀원 간 동일한 방향을 바라보기 위해서는 기준과 목표를 명확히 맞추는 과정이 필요하다
- 처음부터 완벽할 수는 없기 때문에, 빠른 결정 후 더 나은 방향이 보이면 수정하는 방향이 필요하다

---

#### 문제 & 해결 (Problem & Solution)

- **문제**
  - 기존 기획이 구체화될수록 방향성이 모호해지고 팀원 간 이해 차이가 발생함

- **원인**
  - 초기 단계에서 서비스 목표와 기준이 명확하게 정리되지 않았음

- **해결**
  - 기획을 유지하기보다 과감하게 방향을 수정
  - 팀 미팅을 통해 공통된 목표와 기준을 다시 정의

---

#### 느낀 점 (Insight)

- 같은 방향을 보고 있다고 생각해도, 기준이 다르면 다른 결과로 이어질 수 있다
- 초기 방향 설정이 이후 전체 흐름에 큰 영향을 준다는 것을 체감했다

---

#### 내일 할 것 (Next)

- MVP 선정 및 핵심 기능 정의
- 기능별 역할 분리 기준 정리

---

#### 한줄 다짐

- 완성도 있는 서비스를 개발하기 위해 빠른 판단을 하자!

---

#### 배운 것 (What I learned)

- 기능 정의만으로는 부족하고, 사용자가 어떻게 서비스를 이용하는지 흐름으로 정리해야 한다
- 데이터 구조 설계는 서비스 구조를 결정하는 중요한 요소다

---

- 화면이 아니라 사용자 행동을 기준으로 설계해야 서비스가 자연스럽게 이어진다

### 📘 0424 · Fri

#### 오늘 한 일 (What I did)

- ERD 변경 사항 검토 및 수정
- 데이터 표현 방식에 대한 팀원 간 논의
- API 명세서 정리 및 통합
- GPS 드로잉 기능 PoC 진행

---

#### 배운 것 (What I learned)

- API는 처음부터 구조를 잘 설계하면 중복 없이 효율적으로 구성할 수 있다
- 팀원 간 데이터 표현 방식이 다르면 개발 과정에서 혼선이 생길 수 있다

---

#### 문제 & 해결 (Problem & Solution)

- 문제
  - ERD 설계 과정에서 데이터 표현 방식이 팀원마다 다르게 이해됨
  - API가 기능별로 분리되면서 중복되는 구조 발생

- 원인
  - 데이터 정의 기준이 명확하지 않았음
  - API 설계 시 전체 흐름을 고려하지 않고 부분적으로 작성

- 해결
  - ERD 기준을 다시 정리하고 팀원 간 동일한 기준으로 통일
  - API를 기능 단위가 아닌 흐름 단위로 재정리하여 통합

---

#### 느낀 점 (Insight)

- 초기 데이터 설계가 명확해야 이후 개발이 안정적으로 진행된다
- 전체 흐름을 보고 설계하면 불필요한 중복을 줄일 수 있다

---

- API 기반 기능 구현 시작
