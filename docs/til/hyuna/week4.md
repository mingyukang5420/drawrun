### 클라이언트 설계 과정

이번 주는 Flutter를 처음 사용하면서 단순 기능 구현을 넘어서,  
기술 선택과 구조 설계에 대해 고민하게 된 시간이었다.

---

#### 1. Flutter 개발 흐름과 초기 설계

초기 개발 단계에서 Flutter 에 대한 지식이 부족했기 때문에,
익숙한 방식인 React 처럼 단계별로 작업을 추가해나가는 방식으로 개발을 진행했다.

- 프로젝트 생성 및 환경 세팅
- Naver Map SDK를 활용하여 지도 화면 구성
- 앱 특성상 URL 접근이 불가능하기 때문에 하단 네비게이션을 추가하여 라우팅 처리
- 지도 컴포넌트를 공통으로 사용하기 위해 shared 영역으로 분리
- 이후 도메인 기반으로 feature 디렉토리 구조 설계

처음에는 문제없이 진행되는 것처럼 보였지만,  
작업을 이어갈수록 구조에 대한 문제가 드러났다.

- 코드 위치에 대한 기준이 모호해짐 → 협업 어려움
- 공통화 기준이 흔들림
- 기능이 늘어날수록 작업 속도가 느려짐

React에서는 구현을 하면서 구조를 정리해도 큰 문제가 없었지만,  
Flutter에서는 구조 없이 구현을 먼저 진행하는 방식이 오히려 비효율적으로 느껴졌다.

---

#### 2. 개발 환경과 실행 과정에서의 어려움

Flutter는 단순히 코드만 작성하면 되는 환경이 아니었다.

- 에뮬레이터 실행 및 디바이스 연결 문제
- SDK 및 패키지 버전 충돌
- Android 환경 설정 이슈
- 작은 수정 이후에도 clean 빌드를 해야 하는 상황

특히 코드가 잘 동작하는지 확인하는 과정이 쉽지 않았다.

- 개발 환경 수정 후 바로 결과를 확인하기 어려움
- 어디서 문제가 발생했는지 파악이 어려움
- 정상 동작 기준 자체가 불명확한 경우 발생
- 버전마다 지원하는 메서드나 방식이 다름으로 cli로도 한번에 수정이 어려움

React 에서는 브라우저 기반으로 빠르게 확인이 가능했지만,  
Flutter 에서는 실행 환경까지 포함해서 관리해야 한다는 점이 부담으로 다가왔다.

---

#### 3. 구조 설계와 클린 아키텍처에 대한 고민

도메인 기반으로 구조를 설계하면서 초기 구조는 다음과 같이 단순하게 시작했다.

```
features/course/
├── controller/course_controller.dart
├── screen/course_screen.dart
└── widgets/course_map_view.dart
```

하지만 작업을 진행하면서 controller의 역할과  
데이터 흐름이 점점 모호해지는 문제가 발생했다.

이 과정에서 flutter 의 구조를 공부하며 클린 아키텍처를 접하게 되었지만 그대로 도입하기에는 부담이 있었다.

- 과도한 디렉토리 중첩으로 복잡도 증가
- 구조 파악 및 개발 속도 저하
- 팀 전체 러닝 커브 증가

결국 클린 아키텍처를 그대로 사용하는 대신,

- 기존 controller 가 하는 역할을 명확하게 하기 위해 MVVM 패턴을 도입하고(controller → viewmodel)
- 제 3자가 보아도 명확하게 이해할 수 있도록 필요한 개념만 가져온 라이트 클린 아키텍초 구조

로 재구성하였다.

```
course/
 ├── presentation/
 │    ├── screen/
 │    ├── widgets/
 │    └── course_viewmodel.dart
 │
 ├── domain/
 │    ├── course.dart
 │    └── course_repository.dart
 │
 └── data/
      ├── course_repository_impl.dart
      └── course_remote_datasource.dart
```

이 구조를 통해

- 책임 분리 유지
- 구조 이해도 확보
- 개발 속도 유지

세 가지를 균형 있게 가져갈 수 있었다.

#### 4. 상태관리 전환 과정에서의 충돌 (Provider → Riverpod)

이번 프로젝트에서 상태관리는 단순한 UI 상태가 아니라  
실제 데이터 흐름과 연결된 문제였기 때문에 가장 걱정이 큰 부분이었다.

예를 들어

- 러닝 중 데이터가 계속 쌓이는 상황에서  
  러닝이 정상 종료 될 때까지 데이터가 유지되어야 하는 문제

- 지도 위에 표시할 데이터를 API로 받아오고  
  이를 지속적으로 유지하거나 갱신해야 하는 문제

즉, 상태관리는 단순한 값 관리가 아니라  
“데이터 흐름을 어떻게 유지할 것인가”의 문제였다.

---

초기에는 AI가 추천한 Provider를 사용하여 빠르게 시작했다.

하지만 개발을 진행하면서 Riverpod을 접하게 되었고
"더 좋은 방안이 있는데 쓰지 않을 이유가 있나?" 라는 단순한 욕심때문에 전환을 시도했다.

하지만 이 과정에서 정말 큰 문제가 발생했다.

- 기존 Provider 기반 코드와 충돌 발생
- 의존성 제거 과정에서 코드 깨짐
- 팀원 코드와 연결 부분에서 오류 발생
- 전체 흐름이 깨지면서 디버깅 시간 증가

가장 큰 문제는 도입 방식이었다.

- 점진적 도입이 아니라 한 번에 전환 시도
- 구조 안정화 이전에 기술 변경

분명 협업 시 팀원이 아직 상태관리를 사용하지 않았다고 했음에도,,

결과적으로

- 개발 속도 저하
- 불필요한 리팩토링 증가

라는 문제가 발생했다.

이 경험을 통해

- 기술 전환은 단계적으로 진행해야 한다
- 구조가 안정된 이후에 변경해야 한다

는 눈물겨운 깨달음을 얻었다.

결국 이번 선택은 “성장”에 대한 욕심이었지만, 실무에서는 모든 상황을 고려하여 작업할 것 명심..

#### 5. Naver Map SDK 선택 과정에서의 판단 기준

SDK를 선택하는 과정에서도 중요한 경험을 했다.

| 기능           | 0.6.1 | 1.4.4 |
| -------------- | ----- | ----- |
| 마커 클릭      | ⭕    | ❌    |
| 마커 드래그    | ⭕    | ❌    |
| overlay 이벤트 | ⭕    | ❌    |
| 지도 클릭      | ⭕    | ⭕    |
| polyline 표시  | ⭕    | ⭕    |
| 에디터 구현    | ⭕    | ❌    |

초기에는 최신 버전을 사용하는 것이 좋은 선택이라고 생각했지만,
실제 적용 과정에서는 다음과 같은 문제가 발생했다.

- 버전 호환성 이슈
- 설정 충돌
- 플랫폼별 차이

왜 버전 업이 되었는데 기능이 제한되었지? 라는 의문이 들었고,
확인해보니 다음과 같은 방향 차이가 있었다.

0.6.x → 인터랙션 중심 (편집 가능)
1.4.x → 지도 표시 중심 (안정성 + 표준화)

즉, 의도적으로 인터랙션을 제한하고 안정성을 우선시한 구조였다.

---

그렇다면 당연히 이전 버전을 사용하면 되지 않을까 생각했지만,
선택 기준을 다시 정리하여 고민해보았다.

- 무조건 최신이 아니라 안정적인가
- 우리 서비스에서 문제없이 동작하는가
- 장기적으로 유지보수가 가능한가

또한 하나 더 중요한 기준이 생겼다.

- SDK 기능에 의존할 것인가, 아니면 우리가 직접 데이터를 설계하고 처리할 것인가

결론적으로 에디터 기능만 놓고 보면
0.6.x 버전이 더 유리했지만,

- SDK 의존적인 구조는 확장성에 한계가 있고
- 안정성이 떨어지는 리스크가 존재하며
- 우리가 의도한 "데이터 기반 처리 및 계산 구조"와 맞지 않았다

그래서

- 지도는 안정적으로 표현하는 역할로 한정하고
- 경로 생성 및 편집은 서버 기반 데이터 처리로 전환

하는 방향을 선택했고,
그에 따라 1.4.4 버전을 차용하게 되었다.

이 선택은 단순히 기능을 포기한 것이 아니라,

- 안정성 확보
- 유지보수 용이성
- 데이터 처리 중심 구조 설계
- 기술적 성장 관점

을 함께 고려한 결정이었다.
