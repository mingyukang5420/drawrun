---

#### 배운 것 (What I learned)

- [Reader's Eye](https://www.kh.or.kr/brd/board/1209/L/menu/1228?thisPage=3&brdType=&bbIdx=&searchCategory=&searchField=book&searchText=)는 국내 아이트래킹 기반 서비스로, **별도의 외부 카메라 장비를 요구**하는 하드웨어 의존형 구조임을 확인했다. 읽기 훈련 방법을 안내하고 서비스 내에서 직접 훈련시키는 구조였다.
- `Gaze-Tracking` 오픈소스는 화면상의 시선 좌표를 추적하는 것이 아니라, **사용자 기준 정면·상·하·좌·우 방향 중 어디를 응시하는지를 분류**하는 방식임을 확인했다. 목적과 구조가 다른 도구였다.
- 국가유산진흥원 무료 도서는 이미지 기반 스캔본이 주를 이루어, 텍스트 추출이나 e-book 플로우 적용에는 적합하지 않다고 판단했다.
- Visual.camp의 아이트래킹 기술은 **원천기술 수준으로 난이도가 매우 높으며**, iOS 기반으로 개발 중임을 지인을 통해 확인했다. 웹 또는 안드로이드 환경에서의 직접 구현보다는 기업용 SDK 활용 경로를 검토할 필요가 있다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - `Gaze-Tracking` 오픈소스 실행 시 `cmake` 버전 불일치로 빌드 실패
  - 프로젝트에 활용할 무료 e-book 소스를 찾았으나, 국가유산진흥원 도서가 이미지 위주라 텍스트 기반 처리가 어렵다.
- **원인:**
  - `cmake` 요구 버전과 로컬 환경의 버전이 맞지 않아 빌드 환경 구성 실패
  - 해당 도서들이 스캔 이미지 형태로 제공되어 구조화된 텍스트 데이터로 활용하기 어렵다.
- **해결:**
  - 저작권 문제가 없는 도서 데이터는 **사용자가 직접 소유한 데이터를 입력받는 방식**으로 방향을 전환했다.

### 📘 0414 · Tue

#### 오늘 한 일 (What I did)

- 웹캠 기반 오픈소스 시선 추적기(GazeFollower)에 Y축 캘리브레이션 기능 구현
- SeeSo SDK 기능 역설계 — Eye Scroll / Gaze Auto Scroll / Gaze Page Turner 구현
- 시선 추적 파이프라인에 I-DT Fixation Detection, Y 회귀 보정, IDW 보정맵 통합
- 캘리브레이션 UX 개선 (뷰포트 전체 분산 타겟, grace period, 자동 수락)
- WebSocket 재연결 로직 개선 (무한 재시도 + 지수 백오프)

---

#### 배운 것 (What I learned)

- **캘리브레이션의 본질**: "gaze가 타겟에 도달해야 수락"이 아니라 "타겟을 볼 때 gaze가 어디를 찍는지 측정"하는 것이 목적 — 바이어스가 클수록 도달 조건을 걸면 캘리 자체가 불가능해진다
- **RL의 전제 조건**: ground truth 없이 학습하면 오히려 보정맵을 오염시킴 — 읽기 중 줄 확정은 근사치일 뿐, 캘리브레이션만이 신뢰할 수 있는 ground truth
- **Y 회귀 + IDW 분리**: 체계적 수직 바이어스(전체 drift)는 Y 선형 회귀로, 위치별 잔차 오차는 IDW로 — 둘이 같은 데이터 소스를 써야 이중 보정을 피할 수 있다

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 화면 하단 캘리브레이션 포인트가 아무리 응시해도 수락되지 않음
  - WebSocket 연결이 자주 끊기고 복구되지 않음
- **원인:**
  - 하단을 봐도 gaze 포인터가 중앙에 머무는 것이 바로 교정해야 할 바이어스인데, 수락 조건이 "포인터가 타겟 근처에 와야 함"이라 영원히 충족 불가
  - WebSocket 재시도 횟수가 5회로 제한되어 있었음
- **해결:**
  - 수락 조건을 tolerance 범위 진입 → fixation 안정 시간 누적으로 변경. 어디를 찍든 타겟을 바라보는 동안의 gaze 값을 그대로 수집해서 회귀 학습에 활용
  - maxRetries를 Infinity로 변경, 지수 백오프(1.5s → 최대 10s) 적용

---

#### 느낀 점 (Insight)

- 보정 시스템을 만들 때 "뭘 모르는지"를 먼저 파악해야 한다 — 측정값이 틀렸을 때 그 틀림 자체가 데이터다
- RL은 강력한 도구지만 reward 신호가 신뢰할 수 없으면 안 쓰는 게 낫다
- 기술 이름(RL, Bandit)보다 실제로 하는 일(온라인 IDW 누적)을 정확히 이해하는 게 먼저
