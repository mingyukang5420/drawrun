#### 배운 것 (What I learned)

- [Reader's Eye](https://www.kh.or.kr/brd/board/1209/L/menu/1228?thisPage=3&brdType=&bbIdx=&searchCategory=&searchField=book&searchText=)는 국내 아이트래킹 기반 서비스로, **별도의 외부 카메라 장비를 요구**하는 하드웨어 의존형 구조임을 확인했다. 읽기 훈련 방법을 안내하고 서비스 내에서 직접 훈련시키는 구조였다.
- `Gaze-Tracking` 오픈소스는 화면상의 시선 좌표를 추적하는 것이 아니라, **사용자 기준 정면·상·하·좌·우 방향 중 어디를 응시하는지를 분류**하는 방식임을 확인했다. 목적과 구조가 다른 도구였다.
- 국가유산진흥원 무료 도서는 이미지 기반 스캔본이 주를 이루어, 텍스트 추출이나 e-book 플로우 적용에는 적합하지 않다고 판단했다.
- Visual.camp의 아이트래킹 기술은 **원천기술 수준으로 난이도가 매우 높으며**, iOS 기반으로 개발 중임을 지인을 통해 확인했다. 웹 또는 안드로이드 환경에서의 직접 구현보다는 기업용 SDK 활용 경로를 검토할 필요가 있다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - `Gaze-Tracking` 오픈소스 실행 시 `cmake` 버전 불일치로 빌드 실패
  - 프로젝트에 활용할 무료 e-book 소스를 찾았으나, 국가유산진흥원 도서가 이미지 위주라 텍스트 기반 처리가 어렵다.
- **원인:**
  - `cmake` 요구 버전과 로컬 환경의 버전이 맞지 않아 빌드 환경 구성 실패
  - 해당 도서들이 스캔 이미지 형태로 제공되어 구조화된 텍스트 데이터로 활용하기 어렵다.
- **해결:**
  - 저작권 문제가 없는 도서 데이터는 **사용자가 직접 소유한 데이터를 입력받는 방식**으로 방향을 전환했다.

### 📘 0414 · Tue

#### 오늘 한 일 (What I did)

- 웹캠 기반 오픈소스 시선 추적기(GazeFollower)에 Y축 캘리브레이션 기능 구현
- SeeSo SDK 기능 역설계 — Eye Scroll / Gaze Auto Scroll / Gaze Page Turner 구현
- 시선 추적 파이프라인에 I-DT Fixation Detection, Y 회귀 보정, IDW 보정맵 통합
- 캘리브레이션 UX 개선 (뷰포트 전체 분산 타겟, grace period, 자동 수락)
- WebSocket 재연결 로직 개선 (무한 재시도 + 지수 백오프)

---

#### 배운 것 (What I learned)

- **캘리브레이션의 본질**: "gaze가 타겟에 도달해야 수락"이 아니라 "타겟을 볼 때 gaze가 어디를 찍는지 측정"하는 것이 목적 — 바이어스가 클수록 도달 조건을 걸면 캘리 자체가 불가능해진다
- **RL의 전제 조건**: ground truth 없이 학습하면 오히려 보정맵을 오염시킴 — 읽기 중 줄 확정은 근사치일 뿐, 캘리브레이션만이 신뢰할 수 있는 ground truth
- **Y 회귀 + IDW 분리**: 체계적 수직 바이어스(전체 drift)는 Y 선형 회귀로, 위치별 잔차 오차는 IDW로 — 둘이 같은 데이터 소스를 써야 이중 보정을 피할 수 있다

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 화면 하단 캘리브레이션 포인트가 아무리 응시해도 수락되지 않음
  - WebSocket 연결이 자주 끊기고 복구되지 않음
- **원인:**
  - 하단을 봐도 gaze 포인터가 중앙에 머무는 것이 바로 교정해야 할 바이어스인데, 수락 조건이 "포인터가 타겟 근처에 와야 함"이라 영원히 충족 불가
  - WebSocket 재시도 횟수가 5회로 제한되어 있었음
- **해결:**
  - 수락 조건을 tolerance 범위 진입 → fixation 안정 시간 누적으로 변경. 어디를 찍든 타겟을 바라보는 동안의 gaze 값을 그대로 수집해서 회귀 학습에 활용
  - maxRetries를 Infinity로 변경, 지수 백오프(1.5s → 최대 10s) 적용

---

#### 느낀 점 (Insight)

- 보정 시스템을 만들 때 "뭘 모르는지"를 먼저 파악해야 한다 — 측정값이 틀렸을 때 그 틀림 자체가 데이터다
- RL은 강력한 도구지만 reward 신호가 신뢰할 수 없으면 안 쓰는 게 낫다
- 기술 이름(RL, Bandit)보다 실제로 하는 일(온라인 IDW 누적)을 정확히 이해하는 게 먼저

---

#### 내일 할 것 (Next)

- 캘리브레이션 결과 적용 후 실제 줄 감지 정확도 측정
- Eye Scroll / Page Turner 모드 실사용 테스트
- 시선 추적 기반 리딩 서비스 PoC 완성도 검토

### 📘 0415 · Wed

#### 오늘 한 일 (What I did)

- 컨설턴트님의 피드백 반영 후 이지리딩 기획 방향 재검토 (스마트 글래스 기반 선행 연구, 프롬프터 출력 형태 검토)
- 오전 기획회의 진행 (새 아이디어 방향으로 논의, 뚜렷한 진전 없음)
- `GP-TSM (Grammar-Preserving Text Saliency Modulation)` 논문 탐색 및 정독 ([ACM CHI 2024](https://dl.acm.org/doi/10.1145/3613904.3642699)) — LLM 기반 재귀 문장 압축으로 단어별 현저성(saliency)을 산출하고, 문법 보존 상태에서 불투명도 조절로 중요도를 시각화하는 텍스트 렌더링 기법
- 팀원 간 이해도 싱크 및 기술 충분성 평가 논의
- 논문 내용 재검토 후 팀원들에게 정정 안내, 진행 여부 재확인
- GPU 서버 신규 발급 필요 여부 검토 시작
- 취업특강 참석
- 한국어 볼드 처리 파일럿 테스트용 HTML 파일 제작 및 팀 내부 배포 (단문 10문장, 문단 5문항, 응답폼 + 클립보드 복사 기능 포함)

---

#### 배운 것 (What I learned)

- 탐색한 논문의 핵심 메커니즘: `GP-TSM`은 LLM으로 재귀적 문장 압축을 수행해 핵심 의미에서 멀어질수록 해당 단어를 점점 낮은 opacity로 렌더링한다. **볼드가 아닌 opacity 조절**로 중요도를 표현하며, 문법적 완결성을 유지하는 것이 핵심이다.
- 논문을 얕게 읽으면 팀 내 공유 과정에서 **오해와 정정 비용이 발생**한다는 것을 직접 경험했다.
- 한국어 볼드 처리 시 형태소 분석 이후 **어간만 볼드할지, 어간+어미 모두 볼드할지**가 UX 상 유의미한 변수가 될 수 있다.
- 기획 방향이 막혔을 때, 출력 형태나 디바이스 전제를 바꾸는 것만으로도 **가능성의 프레임 자체가 달라질 수 있다**는 것을 컨설턴트님의 피드백을 통해 느꼈다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 팀원들의 기획 파기 의견이 있었으나, 컨설턴트님의 피드백 이후 방향이 다시 열렸고 팀 내 이해도 차이가 발생했다.
  - 논문을 충분히 읽지 않은 상태로 팀에 공유하여 잘못된 내용이 전달됐다.
  - 기술 충분성에 대한 팀원 간 의견이 갈렸고, 아직 의견을 듣지 못한 팀원도 있는 상태다.
- **원인:**
  - 기획 논의와 병행하면서 논문 정독에 충분한 시간을 확보하지 못했다.
  - 팀 내 역할 분담이 아직 구체화되지 않아 각자의 기술적 성장 지점이 불명확하다.
- **해결:**
  - 논문을 오후에 보충 정독 후 팀에 정정 안내, 현재 방향으로 일단 진행하기로 결정.
  - 실제 업무 배정 이후 기술 추가 여부를 재논의하기로 함.
  - GPU 서버 필요 여부는 추가 검토 후 논의 예정.

---

#### 느낀 점 (Insight)

- 논문은 결론만 빠르게 읽는 것과 메커니즘까지 이해하는 것 사이의 간극이 크다. **공유 전에 충분히 읽는 것이 결국 더 빠르다.**
- 컨설턴트님의 피드백이 기술적 해결책이 아니라 **전제 조건을 바꾸는 방식**이었다는 점이 인상적이었다. 막혔을 때 조건을 재설정하는 것 자체가 하나의 방법론이 될 수 있다.

- **해결:**
  - `gemma4-e4b` 모델로 하향 조정 후, Google Cloud 무료 크레딧으로 비용 충당
  - 문서를 기반으로 서로의 이해를 직접 확인하는 토의를 통해 합의점 도출

---

- 우선순위 충돌은 지난주부터 쌓아온 팀워크로 부드럽게 넘겼다. **단단한 관계는 갈등을 없애는 게 아니라 갈등을 다루는 방식을 바꾼다**는 걸 느꼈다.

#### 배운 것 (What I learned)

- **기존 아이디어를 섞고 비틀고 결합하는 것 자체가 새로운 아이디어를 만드는 방법**이 될 수 있다는 것을 컨설턴트님과의 미팅을 통해 확인했다. 무에서 유를 창조하려는 압박을 내려놓는 것이 오히려 발산에 도움이 된다.
- 서비스의 가치는 기능의 수가 아니라 **"그래서 이걸로 뭘 할건데?"라는 질문에 답할 수 있는가**로 판단된다는 것을 팀 내 토의를 통해 다시 생각하게 됐다.
- 팀원들의 목표 교집합을 서비스로 구현하려면, 웹 환경에서 사용자 니즈를 충족시키는 방향이 현실적인 접근임을 정리했다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 서비스 아웃풋 볼륨이 작다는 의심이 팀 내에서 제기됨
  - 코어 기술 두 가지 모두 검증되지 않아 리스크가 높다고 판단됨
  - 도전적인 기술과 현실적인 솔루션, 두 방향을 동시에 충족하는 서비스 아이디어를 찾기 어려움
- **원인:**
  - 구현 가능성이 불확실한 상태에서 기능 확장을 먼저 고민했던 순서의 문제
  - 이미 시장에 유사 서비스가 존재하거나, 없다면 기술적 한계로 정체된 영역이 많음
- **해결:**
  - 컨설턴트님에게 도움을 요청하여 아이디어 발산 미팅 진행
  - 블라인드 거수로 팀원 선호도를 확인하고, 추가 회의를 통해 방향을 계속 탐색하기로 결정

---

#### 느낀 점 (Insight)

- 다른 팀 발표에서 떠오른 질문을 삼킨 것이 계속 마음에 걸렸다. 태클로 보일까봐, 맥락이 맞지 않을까봐 참았지만, **좋은 질문은 발표자에게도 청중에게도 자산이 된다**는 걸 알면서도 실행하지 못했다. 다음엔 다르게 해보고 싶다.
- 원하는 것이 많을수록 아이디어를 고르기가 어렵다는 것을 체감했다. 기술적 도전, 취업 연계, 사용자 가치, 팀원 목표의 교집합까지 모두 만족시키려다 보면 결국 아무것도 선택하지 못할 수 있다. **어느 시점에는 무언가를 포기하는 결정을 해야 한다.**
- 방향이 정해지지 않은 상태에서 오는 불안감이 있다. 이 감정을 시간 내서 들여다봐야겠다고 생각했다.
