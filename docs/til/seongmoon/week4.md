### 📘 0427 · Mon

#### 오늘 한 일 (What I did)

- Spring Boot 개발 환경 구축
- Google Java Style 코드 스타일 적용
- API 공통 응답 구조 구현
- GlobalExceptionHandler 정의
- Backend Convention 작성

---

#### 배운 것 (What I learned)

- 초기 개발 환경 구축에도 기술 및 버전 선정 근거가 명확하게 필요하다.
- Backend Convention을 확실하게 잡고 시작해야 협업 시 큰 도움이 된다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - GlobalExceptionHandler에서 Spring이 기본적으로 던지는 예외(`MethodArgumentNotValidException`,
      `HttpMessageNotReadableException` 등)와 직접 정의한 커스텀 예외의 응답 형태가 일관되지 않았다.
- **원인:**
    - `@Valid` 검증 실패 등 프레임워크 단계에서 발생하는 예외는 Spring 기본 응답 포맷을 따르고, 비즈니스 로직에서 던지는 커스텀 예외만 공통 응답 구조(
      `ApiResponse`)로 감싸지고 있어 클라이언트 입장에서 응답 스키마가 달라졌다.
- **해결:**
    - 모든 예외 케이스를 `ErrorStatus` enum으로 정규화하고, GlobalExceptionHandler에서 Spring 기본 예외도 별도 핸들러 메서드로 잡아
      동일한 `ApiResponse` 포맷으로 반환하도록 통일했다.

---

#### 느낀 점 (Insight)

- 나 혼자 개발하는 것이 아니라 팀원들과 함께 개발을 하는 것이기 때문에, 어느 정도 주관을 가지고 결정을 하되 논의를 통해 조율을 해야 한다.

### 📘 0428 · Tue

#### 오늘 한 일 (What I did)

- GitLab Webhook 중계 서버 구축

---

#### 배운 것 (What I learned)

- GitLab에서 Mattermost로 직접 알림을 보내는 기본 기능이 존재하지만, 가독성이 떨어져 팀 스타일에 맞게 재가공하는 작업이 중요하다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - GitLab이 보내는 Webhook 페이로드를 Mattermost 메시지 포맷으로 변환할 때, 이벤트 종류(Push, Merge Request, Pipeline 등)마다
      필요한 필드와 표현 방식이 달라 분기 처리가 복잡해졌다.
- **원인:**
    - 모든 이벤트를 하나의 핸들러에서 처리하려다 보니 `if/else` 분기가 늘어나고, 새로운 이벤트 타입이 추가될 때마다 기존 코드를 수정해야 하는 구조가 되었다.
- **해결:**
    - 이벤트 타입별로 메시지 변환 로직을 분리하고, GitLab의 `X-Gitlab-Event` 헤더를 기준으로 적절한 핸들러로 라우팅하도록 구조를 잡았다. 이후 새로운
      이벤트가 추가되어도 기존 로직을 건드리지 않고 핸들러만 추가하면 되도록 설계했다.

---

#### 느낀 점 (Insight)

- 알림이 즉시 전달되어 모든 팀원이 동시에 상황을 인지하는 것이 빠른 대응에 큰 도움이 된다.

### 📘 0429 · Wed

#### 오늘 한 일 (What I did)

- Jenkins Webhook 중계 서버 구축
- Flutter 작업을 위한 학습 시작

---

#### 배운 것 (What I learned)

- Jenkins 플러그인을 통해 HTTP 요청을 중계 서버로 보낼 수 있지만, 마지막 업데이트가 2년 전이라 직접 파이프라인 스테이지 안에서 `curl`로 알림을 전송해야 했다.
- Flutter는 텍스트, 버튼, 레이아웃 등 모든 UI 요소가 위젯(Widget)으로 이루어져 있다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - Jenkins에서 빌드 결과를 중계 서버로 전달할 때, 사용 가능한 Notification 플러그인의 마지막 업데이트가 2년 전이라 현재 Jenkins 버전과 호환성
      이슈가 발생할 가능성이 있었다.
- **원인:**
    - 플러그인이 더 이상 유지보수되지 않아 최신 Jenkins API와의 호환을 보장할 수 없었고, 새로운 페이로드 필드를 추가하거나 인증 헤더를 커스터마이징하는 데에도
      제약이 있었다.
- **해결:**
    - 플러그인 의존성을 제거하고, Jenkinsfile의 `post` 스테이지에서 `curl`로 직접 중계 서버에 빌드 결과(성공/실패, 브랜치, 커밋 정보 등)를 POST
      하도록 구성했다. 이를 통해 필요한 필드를 자유롭게 추가하고, Jenkins 버전 업그레이드의 영향을 덜 받는 구조로 만들었다.

---

#### 느낀 점 (Insight)

- Mobile FE를 학부 시절 이후로 처음 다뤄 보니 어렵다는 것을 다시 느꼈고, 패키지 구조가 BE와 비슷하면서도 조금씩 다르다는 점이 흥미로웠다.

### 📘 0430 · Thu

#### 오늘 한 일 (What I did)

- FE 러닝 페이지 개발 시작
- 러닝 플로우(시작 → 카운트다운 → 러닝중 → 일시정지 → 결과 + API 저장) 구현 가이드 학습
- 러닝 도메인을 위한 클린 아키텍처-lite 구조(`presentation` / `domain` / `data`) 설계 검토

---

#### 배운 것 (What I learned)

- Flutter에서도 BE와 유사하게 **ViewModel + Repository + RemoteDataSource** 레이어를 분리할 수 있고, 이를 통해 화면(`presentation`)과 도메인 로직, 네트워크 호출의 책임을 명확히 나눌 수 있다.
- `LatLng`(도메인 모델)와 `NLatLng`(지도 SDK 타입)를 분리하고, 변환 지점을 좁게 가둬야 도메인 코드가 SDK에 오염되지 않는다.
- `ChangeNotifierProvider`로 같은 ViewModel 인스턴스를 화면 간에 전달할 때는 `.value` 생성자를 사용해야 상태(GPS 구독, 타이머 등)가 유지된다.
- `dio`의 `DioException`을 그대로 도메인까지 노출시키지 않고, `RemoteDataSource`에서 `ApiException`으로 변환해 던지는 것이 클린한 경계 처리 방식이다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - Flutter 자체에 익숙하지 않은 상태에서 러닝 플로우 구현 가이드를 읽다 보니, 어디서부터 손대야 할지 감이 잡히지 않고 시간만 흘려보냈다.
- **원인:**
  - 가이드가 한 번에 다루는 범위(아키텍처 마이그레이션 + 좌표 타입 통일 + 화면 흐름 + API 연동)가 넓었고, Flutter의 위젯 트리 / Provider / 비동기 스트림 구독 같은 기본 개념이 머릿속에 정리되지 않은 상태에서 구현 디테일부터 보려고 해 흐름을 따라가지 못했다.
- **해결:**
  - 가이드의 "9. 작업 순서" 섹션을 기준으로 PR 단위로 쪼개고, **1단계(controller → viewmodel 마이그레이션 + `LatLng` 통일)** 만 먼저 끝내는 것을 목표로 좁혔다. 그리고 가이드에서 모르는 개념(`ChangeNotifier`, `Consumer`, `StreamSubscription`, 확장 메서드 등)은 별도로 짧게 학습한 뒤 다시 가이드로 돌아오는 방식으로 호흡을 끊었다.

---

#### 느낀 점 (Insight)

- 새로운 기술을 익힐 때 큰 그림(아키텍처)과 디테일(위젯/문법)을 동시에 잡으려고 하면 어느 쪽도 제대로 잡히지 않는다. 작업 단위를 잘게 쪼개고 한 번에 한 레이어씩 이해해 나가는 편이 결과적으로 더 빠르다.
