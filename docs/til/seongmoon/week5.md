---

#### 배운 것 (What I learned)

- 서버와 클라이언트가 주고받는 수치 데이터는 반드시 단위에 대한 합의가 선행되어야 하며, 합의된 단위는 클라이언트 진입/송신 시점에서 한 번 변환해 일관되게 사용해야 한다
- 러닝처럼 실시간 측정값이 많은 도메인에서는 페이스(min/km), 거리(km/m), 시간(sec/ms) 등 단위 혼동이 발생하기 쉬워 변환 헬퍼를 별도로 두는 편이 안전하다
- 결과 화면처럼 정적인 데이터를 보여주는 화면은 위젯 트리를 카드 단위로 분리해두면 이후 항목 추가나 순서 변경에 유연하게 대응할 수 있다

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - `avgPaceSecPerKm` 값을 변환 없이 서버에 전송하여 DB 에 `24472` 같은 비정상적인 값이 저장되던 문제
- **원인:**
    - BE 와 사전에 합의한 단위(min/km)가 있었음에도 FE 전송 단계에서 단위 변환이 누락됨
- **해결:**
    - 전송 직전에 sec/km → min/km 로 변환해 합의된 규격에 맞도록 수정

---

#### 느낀 점 (Insight)

- 같은 파트를 담당한 팀원 간의 소통뿐 아니라, FE-BE 처럼 다른 파트를 맡은 팀원과의 지속적인 소통이 그에 못지않게 중요하다는 것을 다시 한 번 체감했다

### 📘 0507 · Thu

#### 오늘 한 일 (What I did)

- 결과 화면 메트릭 그리드 재구성 (스플릿 → 케이던스로 교체, 항목 배치 변경)
- 진행/결과 화면의 평균 페이스·거리·페이스·칼로리·BPM·케이던스 단위 표기 제거
- 카운트다운 시퀀스에서 `Start!` 단계 삭제 (3 → 2 → 1 → 진행 화면 진입)
- 종료 버튼 롱프레스 시간 3초 → 1초로 단축
- 일시정지·결과 화면 그리드의 `BOTTOM OVERFLOW` 경고 해결
- AndroidManifest 에 백그라운드 위치 / 포그라운드 서비스 권한 추가
- LocationService 에 포그라운드 알림 설정 및 라이프사이클 동기화를 적용해, 화면이 꺼진 상태에서도 거리·경로 측정이 유지되도록 개선
- FE 러닝 케이던스 로직 구현

---

#### 배운 것 (What I learned)

- Android 에서 화면이 꺼진 상태에서도 위치를 지속적으로 받으려면 단순 위치 권한만으로는 부족하고, 포그라운드 서비스(+ 상시 알림)와 백그라운드 위치 권한이 함께 선언/실행되어야 한다
- 위치 추적 같은 장기 실행 작업은 위젯 라이프사이클이 아닌 서비스 라이프사이클에 맞춰야 화면 종료/복귀 시점에 데이터가 끊기지 않는다
- Flutter 의 `OVERFLOW` 경고는 특정 기종에서만 재현되는 경우가 많아, 고정 사이즈 대신 `Expanded`, `Flexible`, `LayoutBuilder` 와 비율 기반 그리드를 활용해 반응형으로 구성해야 한다
- 메트릭 카드처럼 좁은 영역에서는 단위 라벨을 제거하고 값 자체에 집중시키는 편이 정보 가독성과 시인성에 유리하다

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - 일시정지·결과 화면 그리드에서 `BOTTOM OVERFLOW` 경고 발생
- **원인:**
    - 다양한 화면 크기의 기종을 충분히 고려하지 않고, 테스트용 기기 한 종에 맞춰 고정 사이즈 위주로 레이아웃을 구성한 것이 원인
- **해결:**
    - 고정 높이 대신 `Expanded`/`Flexible` 기반의 반응형 레이아웃으로 보정해 다양한 해상도에서 OVERFLOW 가 발생하지 않도록 수정

---

#### 느낀 점 (Insight)

- 단일 기기에서 동작이 잘 된다는 것에 만족하지 않고, 다양한 해상도와 환경에서의 테스트가 반드시 동반되어야 한다는 점을 다시금 느꼈다

### 📘 0508 · Fri

#### 오늘 한 일 (What I did)

- 러닝 종료 및 코스 이미지 서버 전송 API 연동

---

#### 배운 것 (What I learned)

- 컨테이너 환경에서는 애플리케이션이 파일을 정상적으로 저장했더라도, 그 경로가 호스트와 마운트되어 있지 않으면 컨테이너가 재시작되는 순간 데이터가 사라질 수 있다
- 파일 업로드 기능은 BE 응답 코드만으로 정상 동작을 단정할 수 없고, 실제 저장 경로(호스트 볼륨)에 파일이 남는지까지 확인해야 한다
- 인프라 설정은 코드 레벨에서 잡아내기 어려운 이슈를 만들 수 있어, FE/BE 코드뿐 아니라 docker compose 의 volume 설정과 EC2 디스크 경로까지 함께 점검하는 습관이 필요하다

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - 이미지 전송 로직이 BE/FE 양쪽에서 에러 없이 완료되었음에도, 실제 이미지가 서버에 저장되지 않던 문제
- **원인:**
    - Backend 컨테이너의 볼륨과 EC2 호스트 경로가 마운트되어 있지 않아, 업로드된 이미지가 컨테이너 내부 경로에만 존재하고 호스트에는 영속되지 않는 상태였음
- **해결:**
    - Backend 컨테이너와 EC2 호스트 경로를 볼륨으로 마운트하여, 업로드된 이미지가 호스트 파일 시스템에 정상적으로 저장되도록 수정

---

#### 느낀 점 (Insight)

- FE 를 프로젝트에서 메인으로 담당하는 것은 이번이 처음인데, 그동안 BE 를 담당하면서 미처 고려하지 못했던 FE 입장의 제약과 불편함이 적지 않다는 것을 새삼 느꼈다
