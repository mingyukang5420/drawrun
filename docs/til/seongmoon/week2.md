### 📘 0413 · Mon

#### 오늘 한 일 (What I did)

- 서비스 코어 기술인 아이트래킹 POC 진행
  - 사용한 기술
  - MediaPipe
  - EyeTrax
- 두 라이브러리의 내부 구조와 출력 데이터 형식 비교
- 웹 환경에서의 실시간 처리 가능성 검토

---

#### 배운 것 (What I learned)

- **MediaPipe Face Mesh**는 얼굴에 468개의 랜드마크를 실시간으로 추출하지만, 시선(gaze) 좌표를 바로 주지는 않고 눈 주변 랜드마크를 가공해야 한다.
- **EyeTrax**는 내부적으로 MediaPipe 기반으로 동작하는 래퍼 라이브러리로, 시선 좌표를 화면 좌표계로 매핑하는 부분까지 추상화되어 있어 POC 속도를 올리기 좋다.
- 웹캠 기반 아이트래킹은 **사용자별 캘리브레이션(calibration)** 과정이 필수다. 캘리브레이션 없이는 시선 좌표의 오차가 글 단위 추적에는 부적합한 수준이다.
- 아이트래킹 정확도는 **조명, 카메라 각도, 안경 착용 여부**에 따라 편차가 크다. 서비스 UX를 설계할 때 이 변수들을 고려해야 한다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - MediaPipe 단독으로는 "사용자가 지금 화면 어디를 보고 있는지" 좌표를 바로 얻을 수 없음
    - 웹 서비스로 제공하려면 브라우저에서 실시간 처리가 되어야 하는데, 파이썬 기반 라이브러리들은 로컬 실행이 전제
    - 캘리브레이션 없이는 문장 단위 추적이 어려울 정도로 정확도가 떨어짐
- **원인:**
    - MediaPipe는 얼굴 랜드마크 추출까지만 담당하는 저수준 라이브러리라서 시선 추정 로직을 별도로 구현해야 함
    - EyeTrax는 파이썬 환경 중심이라 웹 서비스 배포 구조와 직접 연결되지 않음
    - 웹캠 해상도·사용자 환경(조명, 거리)에 따라 기본 정확도 편차가 큼
- **해결:**
    - POC 단계에서는 EyeTrax로 먼저 **동작 가능성 자체를 검증**하는 방향으로 진행
    - 웹 배포는 WebGazer.js 등 브라우저 기반 라이브러리를 별도 트랙으로 추가 조사하기로 결정
    - 정확도 보완은 단어 단위 추적이 아닌 **문단/구간 단위 추적으로 요구 해상도를 낮추는 방식**을 검토


---

#### 느낀 점 (Insight)

- 아이트래킹 같은 "원천기술에 가까운 기능"은 **우리가 직접 만드는 영역과, 기존 라이브러리로 감당할 영역을 명확히 구분**하는 게 핵심이다. 무리해서 원천기술을 건드리기보다 라이브러리를 어떻게 조합할지 설계하는 것이 더 현실적이다.
- 기획 단계에서 "아이트래킹을 하자"는 한 줄이 실제 구현에서는 **캘리브레이션 UX, 정확도 한계에 맞는 기능 설계, 배포 환경 제약** 세 가지 문제로 갈라진다. 기획서가 단단해도 기술 검증 없이는 비어있는 것과 같다.

---

- 캘리브레이션 UX 레퍼런스 수집 (기존 아이트래킹 서비스들이 어떻게 유도하는지)
- MVP 범위에 아이트래킹을 어느 수준까지 포함할지 팀과 재논의

### 📘 0414 · Tue

#### 오늘 한 일 (What I did)

- 전일 POC 결과 기반으로 아이트래킹 라이브러리 추가 검토
- WebGazer.js, GazeCloudAPI 등 브라우저 기반 라이브러리 비교 조사
- EyeTrax 정확도 측정 테스트 (픽셀 오차, 문장 단위 추적 가능 여부)
- 캘리브레이션 UX 레퍼런스 수집

---

#### 배운 것 (What I learned)

- **WebGazer.js**는 브라우저에서 바로 동작하는 JS 라이브러리라 별도 서버 없이 아이트래킹이 가능하지만, 정확도가 EyeTrax보다 눈에 띄게 낮다.
- 아이트래킹 라이브러리 선택은 **"정확도 vs 배포 용이성"** 트레이드오프다. 웹에서 바로 돌리려면 정확도를 포기해야 하고, 정확도를 잡으려면 별도 처리 서버가 필요하다.
- 캘리브레이션 UX는 대부분 **화면에 점 9~13개를 순차적으로 띄우고 사용자가 응시하는 방식**으로 표준화되어 있다. 새로 설계하기보다 기존 패턴을 따르는 게 사용자 학습 비용을 줄인다.
- EyeTrax의 픽셀 오차는 캘리브레이션 직후에는 작지만, **시간이 지나거나 자세가 바뀌면 급격히 커진다**. 재캘리브레이션 트리거를 UX에 녹여야 한다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - WebGazer.js는 배포는 쉬운데 정확도가 단어/문장 단위 추적에 부적합
    - EyeTrax는 정확도는 나오지만 파이썬 환경이라 웹 서비스 구조와 직접 붙이기 어려움
    - 두 라이브러리 모두 "브라우저에서 바로 + 높은 정확도"를 동시에 만족하지 못함
- **원인:**
    - WebGazer.js는 경량화를 우선해서 연산량을 줄인 구조
    - EyeTrax는 MediaPipe 기반 파이썬 라이브러리라 서버사이드 처리를 전제로 설계됨
    - 웹캠 기반 아이트래킹 자체가 하드웨어 기반 장비(Tobii 등) 대비 정밀도 한계가 명확
- **해결:**
    - 정확도를 우선해서 **EyeTrax를 모델 서버에 두고, 웹 프론트는 웹캠 영상만 전송하는 구조**로 방향 전환 검토
    - 단어 단위 추적은 포기하고 **문단/구간 단위 추적**으로 요구 해상도 조정
    - 내일 FastAPI로 모델 서버 프로토타입 구성해서 실제 연동 가능성 검증 예정

---

#### 느낀 점 (Insight)

- 기술 선택에서 **"하나의 라이브러리로 전부 해결"은 대부분 불가능**하다는 걸 다시 체감했다. 프론트/백엔드/모델을 어떻게 나눌지가 결국 설계의 핵심이다.
- POC는 "되는지 안 되는지" 확인하는 게 끝이 아니라, **"어떤 구조로 붙여야 하는지"까지 나와야** 제대로 된 POC라는 생각이 들었다.
- 정확도 한계를 받아들이고 **기능 스펙을 낮추는 결정**도 엔지니어링의 영역이다. 기획의 이상에 매달리면 구현이 막힌다.

---

#### 내일 할 것 (Next)

- 웹캠 영상 스트림 전송 방식 조사 (WebSocket / WebRTC)
- 프론트 ↔ 모델 서버 연동 POC

### 📘 0415 · Wed

#### 오늘 한 일 (What I did)

- FastAPI 기반 아이트래킹 모델 서버 프로토타입 구성
- EyeTrax를 FastAPI 엔드포인트로 래핑해서 시선 좌표 반환 구조 구현
- 프론트엔드에서 웹캠 프레임을 서버로 전송하는 통신 방식 테스트 (WebSocket)
- 시선 좌표 → 화면상 문단 위치 매핑 로직 초안 작성

---

#### 배운 것 (What I learned)

- FastAPI는 **비동기 처리와 파이썬 ML 라이브러리 호환성**이 좋아서 모델 서버로 쓰기에 적합하다. Flask보다 WebSocket 지원이 기본으로 내장되어 있어 실시간 스트림 처리에 유리하다.
- 웹캠 프레임을 HTTP로 매번 전송하면 레이턴시가 누적되어 실시간 추적이 불가능하다. **WebSocket으로 연결을 유지**하면서 프레임을 스트리밍하는 방식이 현실적이다.
- 프레임을 Base64 문자열로 보내면 네트워크 오버헤드가 커진다. **바이너리 전송(ArrayBuffer)**으로 바꿔야 지연을 줄일 수 있다.
- 시선 좌표와 텍스트 위치를 매핑하려면 **DOM 요소의 위치 정보(getBoundingClientRect)**를 주기적으로 동기화해야 한다. 스크롤이나 리사이즈가 발생할 때마다 매핑이 깨진다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - FastAPI 서버로 웹캠 프레임을 HTTP POST로 보냈더니 초당 2~3프레임밖에 처리가 안 됨
    - 프레임 전송량이 많아서 네트워크 병목 발생
    - 시선 좌표가 나와도 실제 "사용자가 어느 문단을 보고 있는지"로 변환하는 로직이 비어 있음
- **원인:**
    - HTTP는 매 요청마다 연결 수립 비용이 있어서 실시간 스트림에 부적합
    - 프레임을 Base64로 인코딩해서 보내서 페이로드 크기가 불필요하게 큼
    - 시선 좌표(픽셀 단위)와 텍스트 요소(DOM 단위)를 연결하는 중간 레이어가 설계되지 않음
- **해결:**
    - HTTP → **WebSocket 통신**으로 전환, 연결을 유지하며 프레임 스트리밍
    - Base64 → **바이너리 전송**으로 변경해 페이로드 축소
    - 프론트에서 주요 텍스트 요소의 위치를 주기적으로 수집해 서버로 동기화, 서버는 시선 좌표를 문단 ID로 매핑해서 반환하는 구조로 설계

---

#### 느낀 점 (Insight)

- 모델 자체의 정확도만 신경 쓰다가 **네트워크·통신 레이어에서 병목이 생기는 경험**은 예상보다 훨씬 크게 다가왔다. ML POC는 모델 + 전송 + 연동까지 하나의 세트로 봐야 한다.
- FastAPI를 Spring Boot와 역할 분리해서 쓰는 구조(메인 BE는 Spring, 모델 서버는 FastAPI)가 지금 아키텍처에 잘 맞는다는 걸 확인했다. **언어와 프레임워크를 기능별로 나누는 게 억지스럽지 않고 자연스럽다**는 걸 체감했다.
- 시선 좌표라는 "날것의 데이터"를 서비스가 쓸 수 있는 "의미 있는 이벤트(어느 문단을 읽고 있다)"로 바꾸는 중간 레이어가 **실제로 서비스 가치를 만드는 지점**이다. 모델은 도구일 뿐, 가공이 핵심이다.

### 📘 0417 · Fri

#### 오늘 한 일 (What I did)

- 발표 진행
- Electron 기반 데스크톱 앱 환경에서 아이트래킹 재검증
- 웹 환경 대비 카메라 접근 권한·프레임 처리 속도 비교 테스트
- 정확도와 UX 관점에서 도입 가능성 최종 판단
- **Reado 서비스 기획 전면 철회 결정**

---

#### 배운 것 (What I learned)

- Electron은 브라우저보다 **시스템 자원 접근이 자유로워** 카메라 프레임 처리 측면에서 웹보다 유리한 부분이 있다.
- 그러나 **근본적인 한계는 라이브러리나 환경이 아니라 웹캠 아이트래킹 자체의 정확도**라는 걸 확인했다. 환경을 바꿔도 픽셀 단위 오차 자체는 줄지 않았다.
- "기능을 만들 수 있다"와 "서비스에 쓸 수 있다"는 다른 기준이다. **사용자가 매번 캘리브레이션을 해야 하고, 자세가 바뀌면 다시 해야 하는 기능**은 서비스 UX로 성립하기 어렵다.
- 핵심 기술이 서비스 UX를 성립시키지 못하면, **그 위에 쌓은 기획 전체가 흔들린다**.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - 웹 환경 정확도 한계를 Electron으로 보완할 수 있을 거라 기대했지만, 실제로는 유의미한 개선이 없었음
    - 캘리브레이션 UX의 피로도와 자세 변화에 따른 재캘리브레이션 필요성이 서비스 진입 장벽이 됨
- **원인:**
    - 웹캠 기반 아이트래킹은 하드웨어 자체의 한계(해상도, 초점, 조명 의존도)가 소프트웨어로 극복되지 않음
    - Electron은 실행 환경의 자유도를 줄 뿐, 알고리즘의 정확도를 높이지는 못함
- **해결:**
    - **Reado 서비스 기획 자체를 철회**하기로 결정
    - 남은 기간은 새 주제 탐색 및 기술 POC의 방향 재설정에 투자

---

#### 느낀 점 (Insight)

- 이번 주 동안 만들어온 POC와 기획서를 전부 접는 결정은 무거웠지만, **늦게 버리면 손실이 커지는 구조**였다. 지금 접는 편이 다음 주의 밀도를 높이는 유일한 방법이다.
- **실패한 기획도 자산이다**. 타겟 세그먼트 분석, 문제 정의, 경쟁 서비스 리서치, Value Proposition 구성은 다음 프로젝트에서도 그대로 재사용할 수 있는 프레임이다. 기획서를 한 번 제대로 써본 경험은 결과물이 살아남든 아니든 남는다.
- POC 5일은 **"안 된다"를 확인하는 근거**였다. 이 확인이 없었다면 더 많은 시간과 인력이 투입된 뒤에 같은 벽에 부딪혔을 것이다. 빠른 실패는 늦은 성공보다 낫다.
