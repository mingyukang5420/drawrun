- **해결:**

### 📘 0513 · Wed

#### 오늘 한 일 (What I did)

- 러닝 시작 API 후속 리팩토링
  - 시작 API HTTP 메서드 POST → GET 전환 및 주석 정리
  - 응답 처리에서 catch 블록을 분리하여 예외 무음 누락(silent failure) 방지
- 트랙 스냅샷 위젯 공용화
  - 트랙 스냅샷 캡처 위젯을 공용 영역으로 분리
  - 러닝 결과 화면을 공용 트랙 스냅샷 위젯으로 전환

---

#### 배운 것 (What I learned)

- try/catch에서 catch를 하나로 묶어 두면 예외가 다른 예외에 가려져 조용히 사라지는 케이스가 생긴다. 예외 유형별로 catch를 분리하는 게 더 안전하다.
- 공용 위젯으로 분리할 때는 호출부의 책임을 어디까지 줄여줄지 인터페이스 설계가 핵심이다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 러닝 시작 API의 응답 처리 중 일부 예외가 로그도 남기지 않고 사라지는 현상.
- **원인:**
  - catch 블록이 너무 광범위하게 잡혀 있어 처리해야 할 예외가 다른 예외에 묻혀버림.
- **해결:**
  - catch 블록을 예외 유형별로 분리하여 무음 누락을 방지하고, 각 분기에서 명확한 처리/로그를 남기도록 조정.

---

#### 느낀 점 (Insight)

- 같은 위젯이 결과/지도 등 여러 화면에서 쓰이는 경우, 공용화로 빼는 시점을 너무 늦추면 중복 코드가 누적되어 유지보수가 힘들어진다. 두 번째 사용처가 보일 때 바로 빼는 게 깔끔하다.

---

#### 내일 할 것 (Next)

- 북마크 기능 (코스/러닝 화면) 구현

---

#### 한줄 다짐

- 예외는 잡는 것보다 "무엇을 잡았는지" 명확히 하는 게 중요하다.

### 📘 0514 · Thu

#### 오늘 한 일 (What I did)

- 북마크 기능 전반 구현
  - 북마크 데이터 레이어 추가 (DataSource / Repository)
  - 코스 탐색 카드에 북마크 토글 버튼 추가 및 상세 진입 핸들러 연결
  - 러닝 화면 북마크 카드 API 연동
  - 북마크 목록 화면 신설 및 마이페이지/러닝 화면에서 라우팅 연결
  - 코스 완주율과 본인 완주 여부를 분리하여 표시하도록 수정

---

#### 배운 것 (What I learned)

- 동일 카드 UI에 들어가는 "전체 완주율"과 "내 완주 여부"는 의미가 다르므로 UI/데이터 모두 분리해야 사용자 혼동이 없다.
- 북마크처럼 여러 화면(코스 탐색, 러닝, 마이페이지)에서 동시에 노출되는 상태는 Repository에서 단일 진실 소스(Single Source of Truth)로 관리해야 화면 간 동기화가 깨지지 않는다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 코스 카드에서 "완주율"만 표시하다 보니, 본인이 완주했는지 여부를 알 수 없다는 피드백.
- **원인:**
  - 코스 완주율(집계 지표)과 본인 완주 여부(개인 상태)를 같은 필드에 묶어 표현하고 있었음.
- **해결:**
  - 두 값을 분리하여 응답/모델/UI 모두에서 별개 항목으로 다루도록 수정.

---

#### 느낀 점 (Insight)

- 북마크처럼 여러 화면에 걸친 기능은 데이터 레이어를 먼저 깔끔하게 설계해두면, 그 위에 화면을 붙이는 작업은 거의 기계적으로 진행된다. 데이터 레이어에 시간을 들이는 게 결국 가장 빠른 길이다.

---

### 📘 0515 · Fri

#### 오늘 한 일 (What I did)

- 챌린지 기능 신규 작업 시작
  - 챌린지 화면 구현을 위한 목업 데이터 생성
  - BE 스펙이 확정되기 전 단계라 화면 골격을 먼저 잡기 위한 사전 작업으로 진행

---

#### 배운 것 (What I learned)

- BE 스펙이 늦게 확정되는 신규 기능의 경우, 목업 데이터로 화면 골격을 먼저 잡아두면 추후 실제 API가 나왔을 때 데이터 모델만 교체하는 식으로 작업을 빠르게 마무리할 수 있다.
- 목업 데이터를 만들 때도 실제 응답 구조를 추측해서 비슷하게 맞춰 두는 게 나중의 마이그레이션 비용을 크게 줄여준다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 챌린지 API 스펙이 아직 확정되지 않아 화면 작업을 시작하기 어려운 상황.
- **원인:**
  - BE에서 챌린지 도메인 설계가 진행 중이라 응답 구조가 유동적임.
- **해결:**
  - 예상 응답 구조에 가까운 목업 데이터를 만들어 두고, 우선 화면/위젯 단위 작업부터 진행하기로 결정.

---

#### 느낀 점 (Insight)

- 한 주 동안 러닝 진행 / 결과 / 기록 / 시작 API / 북마크 / 챌린지까지 굵직한 흐름을 하나씩 처리하면서, 데이터 레이어 → 상태관리 → UI 순으로 쌓아가는 작업 패턴이 몸에 익은 한 주였다. 다음 주는 챌린지 기능을 본격적으로 완성하는 데 집중하자.
