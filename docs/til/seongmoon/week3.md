- 최종 기획 확정

---

#### 배운 것 (What I learned)

- 의사 결정 단계에서는 "무엇을 할지"만큼이나 "무엇을 하지 않을지"를 정하는 것이 중요하다는 걸 체감했다.
- 다수의 의견을 모두 반영하려 하면 오히려 방향성이 흐려질 수 있고, 일정 수준에서 과감하게 취사선택하는 용기가 필요하다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - 기획안을 하나로 확정하지 못하고 논의가 계속 제자리에서 맴돌았다.
- **원인:**
    - 팀원 전원이 도달하고자 하는 최종 목표는 같았지만, 그 목표에 이르는 접근 방식이 조금씩 달랐다.
- **해결:**
    - 모든 의견을 100% 수용하기보다, 프로젝트 목표에 가장 부합하는 방향을 기준으로 일부 의견은 과감히 배제하고 하나의 안으로 수렴시켰다.

---

#### 느낀 점 (Insight)

- 팀원 모두의 의견을 존중하는 것은 중요하지만, 때로는 프로젝트의 방향성을 위해 일부 의견을 과감히 배제하는 판단도 필요하다.

### 📘 0422 · Wed

#### 오늘 한 일 (What I did)

- 기능 명세서 작성
- 유저 워크플로우 작성 (화면 구조도가 아닌, 사용자 행동 흐름 기준으로 재정리)
- ERD 작성 시작
- API 명세서 작성 시작 (RESTful 규칙 준수)

---

#### 배운 것 (What I learned)

- 처음에 작성했던 "유저 워크플로우"가 실제로는 **화면 구조도(Site Map)**에 가까웠다는 것을 깨달았다. 워크플로우는 시작점과 종료점이 있고, 사용자의 행동에 따라 분기(Decision)되는 흐름 중심으로 그려야 한다는 원칙을 다시 정리했다.
- 모든 설계 문서를 직렬로 한 단계씩 끝내고 넘어가는 것이 안정적으로 보이지만, 기능 명세 · ERD · API 명세는 서로 참조하며 발전하는 문서이기 때문에 병렬로 진행하며 상호 검증하는 편이 오히려 효율적이다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
    - 유저 워크플로우를 그리긴 했는데, 다시 살펴보니 사용자 행동의 흐름이 아니라 화면 간 포함 관계를 나열한 구조도에 가까웠다. 또한 여러 설계 문서를 동시에 진행하려다 보니 작업 우선순위가 흐트러지는 느낌이 들었다.
- **원인:**
    - "워크플로우"라는 용어에 대한 팀 내부의 정의가 명확하지 않았고, 화면 명세와 사용자 흐름을 분리해서 생각하지 않은 채로 작성을 시작했다. 또한 설계 문서 간의 의존 관계를 먼저 정리하지 않고 각자 손에 잡히는 것부터 작업한 점도 영향을 줬다.
- **해결:**
    - 시작점 / 종료점 / 판단(Decision) 노드를 기준으로 워크플로우를 다시 그려, 사용자 행동 흐름 중심의 문서로 재구성했다. 설계 문서 작업은 "동시에 진행하되, 서로 맞물리는 포인트(엔티티·엔드포인트)는 주기적으로 함께 모여 검증"하는 방식으로 역할을 나눴다.

---

#### 느낀 점 (Insight)

- 모든 작업을 전원이 붙어 직렬로 처리할 필요는 없다. 각자 파트를 병렬로 진행하고, 이후 함께 모여 교차 검증만 꼼꼼히 하면 오히려 속도와 품질을 동시에 잡을 수 있다.
- 또한 문서를 작성하기 전에 그 문서가 "무엇을 표현하기 위한 것인지"를 팀 내에서 먼저 정의해 두지 않으면, 결국 다시 그리게 된다는 점을 배웠다.

---

### 📘 0423 · Thu

#### 오늘 한 일 (What I did)

- ERD 작성 완료
- API 명세서 작성 완료 (RESTful 규칙 최종 점검)

---

#### 배운 것 (What I learned)

- 본격적인 개발에 들어가기 전, 작성한 설계 문서들을 팀원 전원이 함께 다시 한번 훑어보는 과정이 반드시 필요하다는 것을 체감했다. 작성자 본인은 이미 머릿속에 그림이 있어 빈 곳을 무의식적으로 채워 읽지만, 처음 보는 팀원의 시선에서는 누락이나 모순이 더 쉽게 드러난다.
- RESTful 규칙은 "URI를 동사 없이 자원 중심으로 짠다" 수준에서 끝나는 것이 아니라, HTTP 메서드 · 상태 코드 · 응답 구조의 일관성까지 함께 고려해야 비로소 규칙을 지켰다고 말할 수 있다는 점을 다시 정리했다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - ERD와 API 명세서를 거의 같은 시점에 마무리하고 보니, 두 문서 사이에서 필드명이 다르게 적혀 있거나, ERD에는 있지만 API 명세서에서는 노출되지 않는 컬럼, 반대로 API 응답에는 존재하는데 ERD에 정의되지 않은 데이터가 발견되었다.
- **원인:**
  - 두 문서를 병렬로 진행하면서, 중간에 변경된 사항을 양쪽 문서에 동시에 반영하지 못했다. 또한 "이 정도는 말 안해도 괜찮겠지" 하고 넘어간 부분들이 작성자에 따라 다르게 해석되어 문서에 반영되었다.
- **해결:**
  - ERD와 API 명세서를 한 화면에 띄워 놓고, 엔티티–엔드포인트–응답 필드를 1:1로 대조하며 불일치 항목을 모두 목록화한 뒤 한 번에 통일했다. 이후로는 한쪽 문서를 수정할 때 반드시 다른 쪽도 함께 검토하는 흐름을 규칙으로 정했다.

---

#### 느낀 점 (Insight)

- 설계 문서는 "작성을 마치는 것"이 아니라 "팀원 전체의 머릿속 그림을 일치시키는 것"이 진짜 목표라는 걸 다시 느꼈다. 문서가 아무리 깔끔해도 팀원들이 동일하게 해석하지 못한다면 결국 개발 단계에서 비용으로 돌아온다.
- 그리고 문서끼리 서로를 검증해 주는 구조(ERD ↔ API 명세서, 기능 명세 ↔ 워크플로우)를 만들어 두면, 누가 한 사람만 실수해도 다른 문서에서 모순이 드러나기 때문에 자연스러운 안전장치가 된다.

### 📘 0424 · Fri

#### 오늘 한 일 (What I did)

- 컨설턴트님 주최 팀 미팅을 통해서 기획서 및 문서 검토
- GPS 드로잉 관련 POC

---

#### 배운 것 (What I learned)

- MVP에 대한 정의를 새롭게 정리했다. 그동안은 "최소한의 기능을 갖춘 하나의 완성된 사이클"이라고 생각해 왔지만, 실제 MVP는 로그인·회원가입 같은 부수 기능까지도 과감히 덜어내고 서비스의 핵심 가치를 검증할 수 있는 가장 작은 단위까지 좁히는 개념이라는 점을 알게 되었다.
- 즉, "이 서비스가 사용자에게 어떤 가치를 주는가?"라는 질문에 답하는 데 필요하지 않은 모든 기능은 MVP에서 빠질 수 있어야 한다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 서비스의 방향성이 점점 모호해지고, 무엇을 핵심으로 내세우는 프로젝트인지 한마디로 설명하기 어려운 상태가 되어 가고 있었다.
- **원인:**
  - 기획 단계에서부터 너무 먼 미래의 업데이트와 확장 기능까지 미리 끌어와 논의하다 보니, 정작 MVP에서 보여줘야 할 핵심 기능이 다른 부가 기능들과 뒤섞여 우선순위가 흐려졌다. 또한 각자 머릿속의 이상적인 완성형을 그리느라, 지금 단계에서 꼭 필요한 것이 무엇인지에 대한 합의가 부족했다.
- **해결:**
  - 서비스의 아이덴티티(핵심 가치)를 한 줄로 다시 정의하고, 그 정의에 직접적으로 기여하지 않는 기능들은 과감히 후순위로 밀거나 MVP 범위에서 제외했다. 남긴 기능들은 "이 기능이 빠지면 서비스가 성립하지 않는가?"라는 기준으로 한 번 더 걸러냈다.

---

#### 느낀 점 (Insight)

- 확장성을 고려한 설계도 분명 중요하지만, 검증되지 않은 가치 위에 쌓아 올린 확장은 사상누각이 될 수 있다. 먼저 핵심 가치를 작은 형태로라도 시장에 내놓아 검증하고, 거기에 애자일하게 살을 붙여 가는 방식이 결국 더 빠르고 안전한 길이라는 것을 느꼈다.
- 또한 "지금 무엇을 만들지"를 명확히 하는 것은 단순한 일정 관리 차원이 아니라, 팀이 같은 방향을 보게 만드는 가장 강력한 수단이라는 걸 다시 한번 느꼈다.
