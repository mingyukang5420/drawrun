#### 배운 것 (What I learned)

- PostgreSQL에서 `SERIAL`은 내부적으로 sequence를 생성하는 shorthand이고, `GENERATED ALWAYS AS IDENTITY`가 SQL 표준이다. 단, 자연 키가 안정적이고 의미를 가진다면 대리 키 없이 그 자체를 PK로 쓰는 것이 더 단순하다.
- 한국 행정구역 코드 체계에서 시/도는 2자리, 구는 3자리를 추가해 5자리면 전국 구 단위를 고유하게 식별할 수 있다. 기상청 파일 기준 `1144000000`에서 앞 5자리 `11440`이 마포구다.
- Overpass API는 `out geom`으로 relation 멤버 way의 geometry를 함께 반환한다. boundary relation의 outer role 세그먼트들은 연결 순서가 보장되지 않아서, 끝점을 1e-6 허용 오차로 매칭해 head-to-tail로 이어붙인 뒤 링을 닫아야 유효한 POLYGON이 된다.
- `ST_Centroid(boundary)`로 중심점을 계산하는 것보다 기상청 공식 격자 좌표를 그대로 쓰는 것이 날씨 API 연동 목적에 더 적합하다. 기상청 격자 좌표는 동 단위 대표 지점 기준으로 산출된 값이기 때문이다.
- `select * from district;`에서 아무것도 안 나오는 것처럼 보인 이유는 `boundary` 컬럼이 수천 개 좌표의 WKT 문자열이라 터미널 출력이 밀려났기 때문이다. `select *`에 geometry 컬럼이 포함되면 `\x` 모드를 쓰거나 필요한 컬럼만 명시하는 것이 낫다.
- `netstat`에서 PID가 두 개 떠 있을 때, 둘 다 `com.docker.backend.exe`와 `wslrelay.exe`면 실제 PostgreSQL 인스턴스는 하나다. Windows에서 Docker가 IPv4(`0.0.0.0:5432`)와 WSL relay(`[::1]:5432`)를 동시에 열어두기 때문에 두 진입점이 같은 컨테이너를 가리킨다.

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - `select * from district;`가 아무것도 반환하지 않는 것처럼 보였음.
  - Python으로 조회하면 2행이 있는데 psql에서는 비어 보여 DB 인스턴스 불일치를 의심했음.
- **원인:**
  - `boundary POLYGON` 컬럼이 수천 개 좌표로 구성된 거대한 WKT 문자열이라, `select *` 출력이 터미널 너비를 초과해 화면 밖으로 밀려난 것이었음.
  - `COUNT(*) = 2`와 `pg_tables` 조회로 데이터가 실제로 존재함을 확인.
- **해결:**
  - geometry 컬럼을 제외한 컬럼만 명시하거나 `\x` expanded mode로 조회.

---

- **문제:**

- **원인:**

- **해결:**
  - 끝점 매칭 시 1e-6 허용 오차 적용 및 역순 세그먼트 뒤집기 로직 추가. 매칭 실패 시 경고 로그 후 None 반환으로 데이터 무결성 보호.

---

#### 느낀 점 (Insight)

- PK 타입 선택은 단순한 기술 선택이 아니라 도메인 의존성 결정이다. 대리 키는 유연하지만 의미가 없고, 자연 키는 의미가 있지만 변경에 취약하다. **행정구역 코드처럼 정부 표준으로 안정적으로 관리되는 키라면 자연 키를 PK로 쓰는 것이 오히려 모델을 명확하게 한다.**
- 공간 데이터를 다룰 때 `select *`는 함정이다. geometry 컬럼은 일반 텍스트 출력에 적합하지 않으므로, 조회 목적에 맞게 컬럼을 명시하거나 `ST_AsText`, `ST_AsGeoJSON`으로 가공해서 보는 습관이 필요하다.
- 커밋 순서도 설계다. import 의존성이 있는 파일을 먼저 커밋해야 각 커밋 시점에서 코드가 실행 가능한 상태를 유지한다. **커밋 히스토리는 작업 순서가 아니라 논리적 빌드 가능 단위여야 한다.**

- 코스 선택 러닝의 완주 판정 로직 백엔드 구현 (테스트 직전 상태)

---

#### 배운 것 (What I learned)

- 기존에는 코스와 에디터를 하나의 테이블에서 관리했는데, 코스는 등록된 코스만 관리하고 에디터는 별도 테이블로 분리했다. **에디터 → 기록 → 코스 순의 단방향 흐름을 확립함으로써 데이터 흐름의 방향성이 명확해졌다.**
- 상태 관리를 `boolean`으로 처리하면 설계자 외에는 의미를 파악하기 어렵다. **팀 단위로 관리하는 코드에서는 커뮤니케이션 비용을 고려해 `ENUM`으로 상태를 표현하는 것이 유지보수 측면에서 더 낫다.**
- ERD 설계 시 JOIN 연산을 줄이려는 의도로 과도하게 압축하면 오히려 로직 분기가 복잡해지고 가독성이 떨어진다. **쿼리 효율보다 개념의 명확한 분리가 먼저다.**
-  개념적 설계 없이 물리적 설계로 바로 진입하면 테이블 구조에 추상적인 개념이 뒤섞인다. **"에디터", "기록", "코스"가 각각 무엇을 의미하는지 먼저 정의하고, 그 관계를 논리적으로 확정한 이후에 테이블로 옮겨야 한다.** 개념이 불명확한 채로 설계하면 팀원마다 같은 테이블을 다르게 해석하는 상황이 생긴다.
- 나만의 ERD 설계 순서가 필요하다는 것을 느꼈다. 처음에는 한 테이블에 한 컬럼까지 최대한 분리하고, 같은 속성끼리 묶고, 중개 테이블을 추가하는 순서로 진행한 뒤 정규화·반정규화를 적용하는 흐름이 맞을 것 같다. **논리적 설계를 먼저 마친 이후에 물리적 설계로 넘어가야 한다.**

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 코스와 에디터를 하나의 테이블에서 관리하다 보니 팀원 간 개념 이해가 달랐고, 흐름도와 엣지 케이스에서 각자 빠뜨린 부분이 있었음.
  - `boolean` 기반 상태 관리로 인해 설계자 외에는 의도를 파악하기 어려운 구조였음.
- **원인:**
  - 쿼리 효율을 고려해 JOIN 연산을 최소화하려다 보니 하나의 테이블에 너무 많은 개념을 압축했음.
  - DB별 쿼리 연산 속도에 대한 이해가 부족한 상태에서 설계를 진행했음.
- **해결:**
  - 코스·에디터 테이블을 분리하고 에디터 → 기록 → 코스 단방향 흐름으로 구조를 재설계했음.
  - `boolean` 상태값을 `ENUM`으로 전환하는 방향으로 의견을 모았음.
  - 쿼리 연산 속도에 대한 추가 학습 필요성을 인식했으며, 이후 설계에서는 논리적 설계를 먼저 완성한 뒤 물리적 설계로 넘어가는 순서를 적용하기로 했음.

---

#### 느낀 점 (Insight)

- ERD를 압축하면 쿼리는 단순해질 수 있지만, **개념이 뭉개지면 팀 전체의 이해도가 떨어지고 커뮤니케이션 비용이 올라간다.** 효율보다 명확함이 먼저다.
- `boolean`은 설계자의 머릿속에서만 의미가 완성된다. 메모 없이는 설계자 본인도 헷갈릴 수 있는 상태값이라면, **처음부터 `ENUM`으로 의도를 코드에 담는 게 맞다.**
- 정규화와 반정규화는 개념은 알고 있었지만, 실제로 적용하는 순서와 기준은 직접 설계를 반복하면서 만들어가야 한다는 것을 느꼈다. **이론을 아는 것과 순서를 갖는 것은 다르다.**

#### 배운 것 (What I learned)

- 완주 판정과 안전 판정 모두 **사용자 트랙에 버퍼를 씌운 뒤 geometry와 intersection한 길이 비율**로 판정하는 동일한 패턴을 사용한다. 완주는 코스 geometry 기준, 안전은 주변 안전 도로 세그먼트 기준으로 분리된다.
  - 완주: `coveredLength / courseLength >= 0.8`, 버퍼 약 55m(`0.0005°`)
  - 안전: `coveredLength / userLength >= 0.8`, 탐색 반경 60m
- 난이도 판정은 거리·평균 오르막 경사·누적 고도 상승 3가지를 각각 독립적으로 판정한 뒤 **가장 높은 난이도를 최종값으로 결정**한다.
- 고도값은 트랙 좌표 각 점에서 `ST_DumpPoints`로 노드를 분해하고 `<->` 연산자로 `osm_ways`의 최근접 노드를 찾아 `elevation_nodes` JSON 배열에서 읽어온다.
- 행정구역 코드처럼 **의미 있는 자연 식별자가 존재하는 경우 auto-increment PK는 불필요**하다. `varchar` 대신 `char(5)`처럼 길이를 좁혀두면 타입 수준에서 제약을 명시할 수 있다.
- 도로 수집이 필요한 구와 경계만 필요한 구를 분리하면 불필요한 `Overpass` / 고도 API 호출을 줄일 수 있다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 스키마와 파이썬 로더 간 PK 컬럼명 불일치로 `districts` 적재 파이프라인이 깨져 있었음.
  - `CourseService`와 `EditorService`에 거리 단일 변수 기반 난이도 판정 로직이 중복 구현되어 있었음.
  - `DISTRICTS` 리스트 하나로 도로 수집 대상과 경계 전용 대상을 함께 관리해 불필요한 API 호출이 발생했음.
- **원인:**
  - 스키마 변경 시 파이썬 로더 전체 파일에 걸친 컬럼명을 일괄 추적하지 않았음.
  - 난이도 판정 로직이 서비스 레이어에 분산된 채로 기능이 추가되면서 중복이 누적됐음.
  - 수집 대상 구분 없이 단일 리스트로 관리하다 보니 도로 데이터가 필요 없는 구까지 Overpass 호출이 발생했음.
- **해결:**
  - 로더 전 파일(`db.py`, `parser.py`, `fetch.py`, `load.py`)을 추적해 컬럼명 일괄 수정.
  - `DifficultyService`를 신규 생성해 3변수 기반 판정 로직으로 고도화하고 중복 구현 제거.
  - `ROUTE_DISTRICTS` / `BOUNDARY_ONLY_DISTRICTS`로 분리해 수집 루프를 역할에 맞게 분기.

---

#### 느낀 점 (Insight)

- 완주 판정과 안전 판정은 같은 패턴(버퍼 + intersection 비율)으로 구현됐다. 하나 끝내고 나니 다른 하나는 구조가 눈에 들어와서 훨씬 빠르게 끝났다.
- 난이도 판정이 거리 하나로만 되던 걸 거리·고도·경사 세 변수로 세분화했다. 단순하게 시작했어도 기준을 늘리면 판정이 정교해진다.
- 목표 6개 중 5개. 아쉬웠는데 늦게까지 붙잡고 마무리하고 나오니까 머리가 상쾌했다. 나는 할 일이 남아있는 걸 부채처럼 느끼는 사람이라는 걸 알았다. 부채라고 느껴지면 지금 당장 한다.

- Jenkins 빌드 미반영 원인 분석 (파이프라인 타임아웃 이슈)

---

#### 배운 것 (What I learned)

- `District` 엔티티에 `boundary` 필드가 DB에는 존재했지만 Java Entity에 매핑되지 않은 상태였다. **DB 컬럼과 Entity 매핑이 일치하는지 확인하는 것이 공간 쿼리 연동의 전제조건이다.**
- `ST_Intersects`로 트랙 WKT와 행정구역 경계를 비교해 코스가 지나는 지역을 자동 역산할 수 있다. 트랙 `geom`을 WKT로 변환 → 교차 district 조회 → `course_district` 일괄 저장 순으로 흐름이 이어진다.
- GitLab 웹페이지에 revert 버튼이 존재한다. **긴급한 상황에서는 콘솔보다 GUI가 빠르고 실수가 적다.**
- `develop` 브랜치가 protected인 경우 revert도 별도 브랜치를 생성해서 MR로 올려야 한다.
- 코드 리뷰 시 눈으로만 파일을 확인하지 말고, **MR용 폴더를 생성하고 `develop` 최신화 후 직접 `pull` → `checkout`해서 빌드까지 확인해야 한다.**
- Jenkins 파이프라인의 빌드 트리거가 MR 오픈·컴플리트 시점인 경우, **타임아웃 값이 GitLab 반영 시간보다 짧으면 Jenkins가 변경사항을 가져오기 전에 빌드를 시작해 최신 커밋이 skip될 수 있다.**

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - MR을 잘못 머지해 `develop` 브랜치 빌드가 깨짐.
  - 러닝 트랙 이미지 저장을 위한 백엔드 마운트 경로 설정을 머지했으나 배포 환경에 반영되지 않음.
- **원인:**
  - 중간에 작업한 내용이 반영되지 않은 채로 merge를 시도했음. 코드 파일만 눈으로 확인하고 실제 빌드 검증을 하지 않았음.
  - Jenkins 파이프라인의 타임아웃 값이 GitLab 반영 시간보다 짧아, Jenkins가 변경사항을 가져오기 전에 빌드를 실행해 해당 커밋이 skip됐음.
- **해결:**
  - GitLab 웹페이지의 revert 버튼으로 빠르게 revert 커밋 생성. revert 브랜치를 별도로 만들어 MR 올려 `develop`에 반영했음.
  - 이후 코드 리뷰 시 직접 checkout해서 빌드 확인하는 방식으로 프로세스를 바꾸기로 했음.
  - Jenkins 로그를 통해 타임아웃 원인을 확인했고, 파이프라인 타임아웃 값 조정이 필요함을 팀장님과 공유했음.

#### 느낀 점 (Insight)

- 데일리 컨텐츠에서 들은 재즈 아티스트 이야기가 인상적이었다. 실수를 한 순간 팀원들이 그것을 틀린 음이 아닌 것처럼 받아줬다는 것, 크로매틱 연주로 다음 음을 통해 빌드업으로 만들어냈다는 것. **실수 자체보다 실수 이후의 태도와 대처가 결과를 결정한다.**
- 초등학교 때부터 가져온 좌우명 "실패는 있어도 후회는 없다"와 오늘 들은 내용이 맥락이 닿았다. 내가 말하는 실패는 "마음에 들지 않는 결과"고, 컨님이 말한 실패는 "최선을 다하지 않은 일"이다. 단어는 같아도 의미가 달랐는데, **과정에 최선을 다하고 실수를 커버하는 태도라는 지점에서 결국 같은 방향을 가리킨다.**
- MVP 범위의 업무가 거의 마무리되어가는 시점에서 코드 리뷰를 하니 배우는 게 확실히 있었다. 남의 코드를 읽는 것 자체가 학습이다.
- revert를 콘솔에서 한 땀씩 치고 있다가 GitLab 웹에 버튼이 있다는 걸 뒤늦게 발견했다. **도구를 먼저 파악해두면 급한 상황에서 소모하는 비용이 줄어든다.**
- Jenkins 이슈를 2시간 동안 추적하면서 인프라 구조를 이곳저곳 뒤져봤다. 사일로를 만들지 않으려고 다른 팀원들의 작업 영역을 기웃거리고 있는데, 놓치는 부분이 많아 힘들기도 하다. **그래도 배울 내용이 많다는 건 성장할 여지가 그만큼 남아있다는 뜻이다.**
