## 📘 0427 · Mon

#### 오늘 한 일 (What I did)

- 팀 내부 과제: 데이터 서빙 및 저장 구조 조사
- `OSM(OpenStreetMap)` 활용 레이어 분석 및 `Overpass API` 조사
- `PostGIS` geometry 타입 선택 (`LINESTRING` vs `POINT[]` vs `MULTILINESTRING`) 비교 검토
- `geometry` vs `geography` 좌표계 트레이드오프 분석
- 완주 판정 방식 설계 및 검증 (`ST_DWithin` 커버리지 기반)
- 랭킹 집계 방식 검토 (실시간 집계 vs Write-time 집계)
- 결정사항 기반 샘플 SQL, API 플로우, Python 검증 스크립트 작성
- 데이터 설계 결정사항 v1~v3 Notion 문서화 및 비교 시각화 이미지 생성

---

#### 배운 것 (What I learned)

- `OSM`은 단일 API가 아니라 용도에 따라 레이어가 나뉜다. 지도 렌더링은 Tile Server, 안전 경로 조회는 `Overpass API`, 완주 검증은 `PostGIS` 자체 처리로 각각 분리하는 것이 맞다.
- `MULTILINESTRING`과 완주 판정 방식(`ST_DWithin`)은 같은 방향을 가리키지만 각각 독립적인 이유로 선택된 것이다. `MULTILINESTRING`은 GPS 끊김 처리 때문이고, `ST_DWithin` 커버리지는 역방향 인정 때문이다. **두 결정을 같은 맥락으로 묶어 이해하면 나중에 혼선이 생긴다.**
- `ST_HausdorffDistance`, `ST_FrechetDistance` 같은 내장 경로 유사도 함수는 시작점과 끝점 위치에 영향을 받는다. 역방향을 인정하고 GPS 끊김 구간이 있는 `MULTILINESTRING` 구조에서는 적합하지 않다.
- `geometry(4326)`으로 저장하고 거리 계산 시에만 `::geography` 캐스팅을 쓰는 절충안으로 인덱스 성능과 미터 단위 정확도를 동시에 확보할 수 있다.
- 랭킹 집계는 MVP 단계에서 실시간 집계로 시작하고 `Partial Index`를 처음부터 걸어두면 성능을 충분히 확보할 수 있다. Write-time 집계 전환은 슬로우쿼리가 실제로 발생하는 시점에 검토하면 된다.
- 경로 썸네일은 간소화 연산 대신 **경로 이미지를 저장한 뒤 사이즈를 줄여 썸네일로 제공하는 방식**으로 결정했다. 간소화는 원본 복원이 불가능하고 GPS 드로잉 품질을 포기하는 것과 같아 폐기했다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - GPS 드로잉 서비스에서 시작점과 끝점을 구분하지 않겠다는 요구사항으로 경로 저장 타입 선택이 불명확했음.
  - 완주 판정에서 역방향을 인정해야 하는데, `LINESTRING`과 내장 유사도 함수로는 처리가 어려웠음.
  - 목록 썸네일에서 매 조회마다 간소화 연산을 실행하는 부하 문제가 있었음.
- **원인:**
  - `MULTILINESTRING` 선택 이유와 완주 판정 방식 선택 이유가 같은 맥락으로 묶여 혼동될 수 있었음.
  - 조회 빈도와 저장 빈도의 비대칭을 고려하지 않고 조회 시점에 모든 연산을 몰아넣었음.
- **해결:**
  - `MULTILINESTRING`과 `ST_DWithin`을 독립적인 결정으로 분리해 각각의 근거를 명확히 했음.
  - 간소화 방식을 폐기하고, 경로 이미지를 저장한 뒤 리사이징하여 썸네일로 제공하는 방식으로 전환했음.
  - 검증 스크립트(Python)를 작성해 `PostGIS` 없이 핵심 로직을 케이스별로 확인했음.

---

#### 느낀 점 (Insight)

- 결정사항을 정리할 때 **"왜 이걸 선택했나"와 "왜 다른 걸 선택하지 않았나"를 함께 써두는 것이 중요하다.** 문서는 결론만 담으면 나중에 맥락을 잃는다. 트레이드오프를 명시해두면 조건이 바뀌었을 때 어떤 결정을 재검토해야 하는지 빠르게 판단할 수 있다.
- 샘플과 검증을 먼저 돌려보면 미확정 항목이 구체적인 숫자로 드러난다. GPS 끊김 150m 케이스가 73%로 미달되는 걸 시뮬레이션으로 확인하기 전까지는 막연히 "반경 20m면 되겠지"라고 생각했다. **설계는 직관만으로 마무리하면 안 된다.**
- 미확정 항목을 문서에 명시적으로 남겨두는 것 자체가 작업이다. 결정되지 않은 것을 모른 척하고 진행하면 나중에 더 큰 비용이 뒤따른다.

## 📘 0428 · Tue

#### 오늘 한 일 (What I did)

- 미사용 브랜치 정리
- ERD PK 타입 결정 (`SERIAL` vs `IDENTITY`) 및 Notion 트러블슈팅 문서화
- 고도 데이터 추가 및 `OSM` 도로 데이터에 적재 방식 결정
- 난이도 계산 정책 결정 및 난이도 가중치 적용 완주율 점수 문서화

---

#### 배운 것 (What I learned)

- 현재 `OSM`에서는 고도 데이터를 제공하지 않아 `Open Elevation API`에서 별도로 수집해야 한다. `Open Elevation`은 Google Elevation API의 무료 오픈소스 대체제로, 위·경도 좌표를 입력하면 해당 지점의 고도값을 미터 단위로 반환한다. 단, SRTM 데이터셋 기반이라 정밀도 한계가 있을 수 있어 검토가 필요하다.
- 코스 노드는 `MULTILINESTRING`으로 관리하지만 이 역시 순서를 가진다. **정방향·역방향 판단은 서비스 로직에서 처리하면 되므로**, 경사도 계산과 오르막/내리막 데이터 가공이 가능하다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 난이도 계산을 위해 고도 데이터가 필요한데 `OSM`에서는 제공하지 않음.
  - DB 구조 변경사항을 팀원에게 공유했지만, 샘플 데이터 적재 스크립트는 업데이트하지 않아 누락이 발생했음.
- **원인:**
  - `OSM` 스펙 한계로 고도 데이터를 후순위로 뒀는데, 난이도 속성을 계산하려면 결국 고도 데이터가 필요했음.
  - ERD와 테이블 생성 스크립트에는 신경을 썼지만, 샘플 데이터 적재 플로우까지 변경 범위를 확장해서 생각하지 못했음.
- **해결:**
  - `Open Elevation API`에서 고도 데이터를 수집해 `OSM` 도로 데이터에 적재하는 방식으로 결정.
  - 팀원이 함께 리뷰하며 누락을 발견해줬고, 같이 점검하는 구조 덕분에 빠르게 대응했음.

---

#### 느낀 점 (Insight)

- 변경사항을 공유할 때 **영향을 받는 모든 플로우를 함께 점검하는 습관이 필요하다.** 스크립트 하나가 빠지는 것처럼 작은 누락도 샘플 데이터 적재 전체를 틀어지게 만든다.
- 내가 만들지 않은 플로우를 그대로 흡수하는 것은 생각보다 훨씬 어렵다. **코드와 구조는 만든 사람의 맥락이 담겨 있고**, 그 맥락 없이 이어받으면 놓치는 부분이 생긴다.
- 같이 리뷰해주는 팀원이 있다는 것이 든든하다. 혼자였다면 더 늦게 발견했을 문제를 함께여서 빠르게 잡을 수 있었다.

- OSM 데이터 수집·적재 파이프라인을 `fetch.py` / `load.py` 2단계 구조로 분리

- `Open Elevation` 공개 서버에 요청을 과도하게 보내 일일 요청 한도를 소진한 것으로 추정, 이후 API 응답 없음

---

#### 배운 것 (What I learned)

- `springdoc`은 `api-docs.path` 설정값을 기준으로 `swagger-config` URL을 자동 생성한다. `config-url`과 `url`을 명시하지 않으면 Nginx의 prefix strip 구조와 충돌해 404가 발생할 수 있다.
- Swagger "Try it out"의 요청 경로는 OpenAPI 스펙의 `servers[].url` 값을 기준으로 구성된다. **`servers.url`이 명시되지 않으면 springdoc이 요청 정보로부터 자동 생성하는데, context-path나 proxy 구조에 따라 경로가 틀어질 수 있다.**
- 로컬 환경의 `context-path /api`와 프로덕션의 nginx `proxy_pass` `/api/` strip은 같은 결과를 만들어낸다. `servers.url = /api`로 고정하면 양쪽 환경 모두 호환된다.
- `Open Elevation`은 공개 서버 기반으로 일일 요청 한도가 존재한다. **배치 사이즈와 호출 간격을 사전에 설계하지 않으면 한도를 빠르게 소진할 수 있다.**
- 파이프라인을 수집(`fetch.py`)과 적재(`load.py`)로 분리하면 운영 환경에서 외부 API에 직접 접근하지 않아도 된다. CSV를 중간 매개체로 두는 구조가 환경 의존성을 낮춘다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 배포 환경에서 Swagger UI 접속 시 `/v1/api-docs/swagger-config` 경로가 404를 반환하며 API 명세 로드 불가.
  - Swagger "Try it out" 실행 시 404 에러 발생.
  - `Open Elevation` 공개 서버 요청 한도 소진으로 고도 데이터 수집 중단.
- **원인:**
  - Nginx가 `/api/` prefix를 strip하고 백엔드로 전달하는 구조에서, springdoc이 자동 생성한 `swagger-config` 경로가 `/api/` location과 매칭되지 않았음.
  - OpenAPI 스펙에 `servers.url`이 명시되지 않아 springdoc이 context-path를 누락한 경로를 자동 생성했음.
  - 배치 사이즈와 호출 간격을 충분히 고려하지 않고 요청을 과도하게 전송했음.
- **해결:**
  - `application.yml`에 `config-url: /api/v1/api-docs/swagger-config`, `url: /api/v1/api-docs` 명시.
  - `OpenApiConfig`에 `servers.url = /api`를 고정해 로컬·프로덕션 양쪽 호환 확인.
  - `Open Elevation` 요청은 내일 재시도 예정. 배치 사이즈와 호출 간격 조정 필요.

---

#### 느낀 점 (Insight)

- AI 도입에 따른 개발자 포지션 변화에 대해 두 진영이 있다는 걸 들으면서, 나는 자연스럽게 새로운 직무가 생길 것이라는 쪽에 서 있다는 걸 확인했다. **도구가 바뀌면 직무가 없어지는 게 아니라 다루는 레이어가 올라간다.**
- `릴리스 AI`, `레브잇` 같은 기업들이 채용 방식을 바꾸고 있다는 사례를 들으면서, 지금 내가 AI를 어떻게 활용하고 있는지를 다시 생각해보게 됐다.
- 공개 API를 사용할 때 한도를 먼저 확인하고 설계에 반영하는 것이 기본임을 다시 확인했다. **무료 공개 서버는 편하지만 안정성을 보장하지 않는다.**
- 파이프라인을 설계할 때 환경 간 의존성을 어떻게 끊을지를 초반부터 고민하면 나중에 구조를 갈아엎는 비용이 줄어든다.
