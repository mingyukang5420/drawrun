#### 오늘 한 일 (What I did)

- 주말 기획 재설계를 위한 사전 준비 진행 (기획 계기, 핵심 가치, 레퍼런스 및 차별점 조사)
- 세 가지 안건 준비 후 팀 회의 기여
- 내부적으로 총 열네 가지 안건 수집 및 투표를 통해 상위 다섯 가지 선정
- 컨설턴트님과 미팅 진행 및 팀원 간 개인 목표 공유
- 새로운 주제 확정 후 기획 빠르게 진행

---

#### 배운 것 (What I learned)

- **팀원들의 표면적인 목표(기술적 성장)와 실제 개인 목표는 달랐다.** 수상, 서비스의 타당성 검증, 인적 네트워크 유지 등 각자의 기대가 다름을 확인했다.
- 투표 기반의 안건 선정 방식이 여러 의견을 효율적으로 수렴하는 데 유효함을 확인했다.
- 모두의 니즈를 파악하고 하나의 방향으로 수렴할 수 있다면, 개인 목표도 함께 달성 가능하다는 것을 알았다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 일정 압박 속에서 팀원 간 목표 차이를 초기에 인식하지 못한 채 기획을 진행했고, 결국 처음부터 다시 하게 됨.
- **원인:**
  - 기한을 맞춰야 한다는 압박이 거시적인 시각을 확보하는 것을 방해했다.
- **해결:**
  - 업무 스트레스가 완화된 주말 시간 동안 각자 깊이 고민하고, 회의에서 개인 목표를 솔직하게 공유함으로써 방향을 재정렬했다.

---

#### 느낀 점 (Insight)

- 일정 압박 속에 있을 때일수록 **의도적으로 한 발 물러서 전체를 바라보는 시간을 만들어야 한다.** 그 여유가 자연스럽게 생기길 기다리면 늦는다.
- 팀 내에서 "다 같이 성장하고 싶다"는 말이 서로 다른 의미를 담고 있을 수 있다. 초반에 개인 목표를 구체적으로 꺼내놓는 것이 불필요한 방향 전환을 막는다.
- 주제가 재미있다 보니 기능 아이디어가 쏟아졌고, 개발 일정 안에 전부 소화할 수 있을지 불확실할 만큼 업무량이 커졌다. 세부 우선순위를 정하면서 현실적으로 쳐내는 과정이 필요하다.

---

## 📘 0421 · Tue

#### 오늘 한 일 (What I did)

- 오전 라이브 수업 수강
- 기획 결정 사항 토의 진행 (MVP 기능 및 사용자 분석 외 항목)
- 개인별 화면 구성 스케치 후 피그마에서 통합 및 플로우 공유
- 전자칠판을 활용한 팀원 간 서비스 플로우 싱크 미팅 진행
- `IA(Information Architecture)` 작성
- 유저 루트 등록 기능 및 품질 검증 방식 토의
- 교보재 안드로이드 기기 수령
- BPM 변주 러닝 음악 기능 관련 레퍼런스 영상 시청

---

#### 배운 것 (What I learned)

- 디자인 전공자 팀원들과 협업하면서 **개발자 시각이 아닌 유저 시각으로 서비스 흐름을 바라보는 접근법**을 어깨너머로 익혔다. 어떤 경험을 제공해야 하는지를 먼저 정의하고 화면을 구성하는 순서가 있다는 것을 알았다.
- 팀원 간 백그라운드가 다를수록 소통 비용이 높아지지만, 그만큼 **현업에서 개발자와 기획자 사이의 커뮤니케이션 역할이 왜 필요한지**를 체감했다.
- 유저가 등록한 루트의 품질 검증 방식으로 좋아요/싫어요 등 커뮤니티 기반 평가보다 **완주율을 점수화하고 난이도별 가중치를 부여하는 방식**이 서비스 목적성을 유지하는 데 더 적합하다는 결론을 냈다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 유저가 러닝 루트를 직접 등록할 수 있는 기능의 안전성 검증과 데이터 품질 오염 우려가 제기됨.
  - BPM 변주 음악 기능의 OS 레벨 처리 여부가 불명확하고, 스트리밍 서비스 연동이 어려워 로컬 파일 기반으로만 테스트해야 하는 한계가 있음.
  - 지도 API에서 경로 데이터를 추출하고 가공하는 방식에 대한 경험이 없어 데이터 확보 방법이 불확실함.
- **원인:**
  - 유저 등록 루트에 커뮤니티 기반 검증을 도입하면 서비스의 목적성이 흐려질 수 있다는 기획적 충돌.
  - BPM 변주 기능이 iOS 전용인지, OS 레벨인지, 앱 레벨인지에 대한 선행 자료가 부족함.
  - 지도 기반 경로 데이터 구조에 대한 사전 경험 없음.
- **해결:**
  - 루트 품질 검증은 완주율 점수화 방식으로 결정. 난이도 산출 로직은 추후 논의 예정.
  - BPM 기능은 우선 로컬 파일 기반으로 테스트하는 방향으로 진행. OS/앱 레벨 처리 여부는 추가 자료 조사 필요.

---

#### 느낀 점 (Insight)

- 디자인 전공자가 팀에 있다는 것이 단순히 시각적 완성도의 문제가 아니라, **서비스를 바라보는 프레임 자체를 넓혀준다**는 것을 오늘 협업을 통해 느꼈다.
- 기획 의도는 좋지만 자료조사, 레퍼런스 확인, 데이터 확보까지 함께 고민할 수 있는 동료의 필요성을 실감했다. **아이디어의 완성도는 혼자보다 같이 검토할 때 높아진다.**
- 한때 데이터 가공과 서빙을 벗어나고 싶어 백엔드 프레임워크 개발자로 전환을 결심했는데, 이번 프로젝트에서 다시 같은 문제를 마주하게 됐다. 피하고 싶었던 영역이 결국 필요한 역량으로 돌아오는 경험이었다.

---

- 문서화 작업 완료 후 설계 및 개발 착수

## 📘 0422 · Wed

#### 오늘 한 일 (What I did)

- 어제 결정한 화면 흐름도 기준으로 팀원 간 기능 이해도 싱크 미팅 진행
- 기능명세서 작성 및 검토 완료
- 인프라팀 / API 명세팀 / ERD 작성팀으로 분업 후 ERD 작성 착수
- `MCP` 기반 캐릭터 생성 자동화 작업 병렬 진행 (이름·컨셉 생성 → 스토리라인 생성 → 이미지 프롬프트 생성)
- BPM 케이던스 기능 폐지 결정
- 캐릭터 애셋 생성 및 뽑기 확률 로직 작업 우선순위 조정

---

#### 배운 것 (What I learned)

- 전날 충분히 논의한 내용도 다음 날 다시 꺼내 싱크를 맞추는 과정이 필요하다. **구두 합의는 생각보다 쉽게 흩어진다.**
- `MCP`를 활용해 액션을 잘게 나누면 (이름·컨셉 → 스토리라인 → 이미지 프롬프트) 복잡한 생성 파이프라인도 모바일 환경에서 명령만으로 운용할 수 있다는 것을 확인했다.
- BPM 메타데이터는 `Spotify API`로 가져올 수 있지만, 기타 음악 스트리밍 서비스 API에는 배속 관련 기능이 없어 범용적인 구현이 불가능함을 확인했다. **기획 의도가 좋아도 API 제약이 실현 가능성을 결정한다.**

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - 전날 논의한 내용임에도 팀원 간 이해도 차이가 존재했음.
  - BPM 케이던스 기능이 저작권 문제와 기술적 한계로 구현 불가 판정.
  - ERD 작업이 오늘 내로 마무리되지 못함.
- **원인:**
  - 전날 과도한 회의로 집중력이 소진된 팀원이 있었고, 구두 논의뿐 아니라 문서화까지 병행했음에도 문서를 재확인할 여력이 남아있지 않았던 것으로 보인다.
  - 음악 스트리밍 서비스 API 대부분이 배속 조절 기능을 미지원하며, 저작권 이슈도 병존.
  - 기능명세서 작업과 병렬로 진행하다 보니 ERD에 투입할 시간이 부족했음.
- **해결:**
  - 오전 싱크 미팅을 통해 화면 흐름도 기준으로 이해도를 재정렬.
  - BPM 기능은 잠정 폐지로 결정.
  - ERD는 내일 추가 시간을 투자해 완성 후 팀 전체 검토 예정.

---

#### 느낀 점 (Insight)

- 와이어프레임을 미리 작업해준 팀원 덕분에 오늘 일정이 크게 단축됐다. **팀에서 누군가가 선제적으로 움직이는 것이 전체 속도에 미치는 영향이 생각보다 크다.**
- 캐릭터 생성 파이프라인을 `MCP`로 자동화하면서, 주요 작업과 병렬로 부가 기능을 진행하는 것이 가능하다는 걸 체감했다. 다만 부가 기능이 주의를 분산시키지 않도록 우선순위 판단은 계속 필요하다.
- 기능 하나를 폐지할 때 아쉬움보다 **팀의 집중력을 지키는 결정**이라고 받아들이는 편이 낫다는 생각이 들었다.

---

- 이미지 생성 프롬프트 완성 후 `GMS API` 자동화 연동 작업 착수
- 설계 완료 후 개발 착수

## 📘 0423 · Thu

#### 오늘 한 일 (What I did)

- ERD 작업 마무리 및 팀 내부 미팅 요청
- ERD 설계 방향 팀 내 의견 공유 및 합의
- API 명세서 팀 전체 검토 및 싱크 미팅 진행

---

#### 배운 것 (What I learned)

- `WHERE` 절 조건이 하나일 때와 두 개일 때의 쿼리 속도 차이는 **레코드가 수백만 건 이상일 때 유의미하게 발생**한다는 것을 확인했다. 설계 결정은 이론보다 서비스의 실제 데이터 규모를 기준으로 판단해야 한다.
- 테이블 분리 여부는 정규화 원칙만의 문제가 아니라, **해당 서비스가 실제로 다룰 데이터 볼륨과 조회 패턴을 함께 고려해야 하는 의사결정**임을 다시 확인했다.

---

#### 문제 & 해결 (Problem & Solution)

- **문제:**
  - API 명세서 검토 중 화면 정의가 되지 않은 기능이 존재해, 기획과 화면 단부터 다시 논의하는 상황이 반복됨.
- **원인:**
  - 일정에 쫓기다 보니 미결 사항을 일단 넘기는 패턴이 반복되고, 이후 단계에서 다시 꺼내 논의하느라 시간이 소모되는 악순환이 이어지고 있다.
- **해결:**
  - 한 명이 전체 초안을 작성한 뒤 팀원 의견을 받아 디펜스하며 진행하거나, 처음부터 모든 논의사항을 결정하고 착수하는 두 가지 방식이 대안으로 거론됐다. 다만 이번에는 두 방식 모두 채택하지 못하고 **일단 넘어가는 방식으로 일관했기 때문에, 해결됐다고 보기는 어렵다.**

---

#### 느낀 점 (Insight)

- 나는 메모리 리소스 확보가 상대적으로 쉽다는 판단 아래 테이블을 분리하는 구조를 선택했지만, 팀원의 의견과 실제 데이터 규모를 검토한 결과 단일 테이블 관리가 더 적합하다는 결론에 도달했다. **설계에 정답은 없고, 맥락이 답을 결정한다.**
- 급하다는 이유로 미결 사항을 넘기면 결국 더 늦은 시점에 더 많은 비용을 치르게 된다. **빠르게 가려면 오히려 멈추고 짚어야 할 때가 있다.**

---

#### 내일 할 것 (Next)

- ERD 설계 기반으로 컨설턴트님과 미팅 진행
- 정규화 및 반정규화 관점에서 현재 설계의 적합성 고민
- 개발 환경 세팅 착수
- 베이스 데이터 확보 방안 조사 및 지도 API가 제공 가능한 데이터 범위 확인

---

#### 한줄 다짐

- 급할수록 미결 사항을 남기지 않는다.
