### 📘 0421 · Tue

#### 오늘 한 일 (What I did)
- 러닝 앱 와이어프레임 작성 및 각 페이지 구성 요소 정의
- 팀원들과 함께 페이지별 UI 요소 및 기능 범위 협의
- MVP 정의 및 Post-MVP 기능 분리 결정

#### 배운 것 (What I learned)
- 지도 표시 방식을 고민할 때, 사용자 추가 기준이 불명확하면 커스텀 맵보다 단순 리스트 뷰가 더 합리적이라는 것
- MVP 범위 설정이 생각보다 판단이 까다롭다는 것 — 기능을 줄이는 게 아니라 핵심을 명확히 하는 작업

#### 문제 & 해결 (Problem & Solution)
- **문제:** 지도에 어떤 기준으로 루트를 표시할지 기준이 없어 UX 설계가 막힘
- **해결:** 사용자 커스텀 추가 방식 대신 리스트 기반 표시로 방향 전환
- **문제:** MVP 범위 결정이 어려웠음 (사용자 커스텀 루트 추가 기능 포함 여부)
- **해결:** 해당 기능은 Post-MVP로 이관, 빠른 MVP 구현 우선

#### 인사이트 (Insight)
- 기능의 복잡도보다 "기준의 유무"가 설계 난이도를 결정한다 — 기준 없는 자유도는 오히려 UX를 어렵게 만듦
- MVP는 기능을 깎는 게 아니라 검증할 핵심을 고르는 것

#### 다음 할 것 (What's Next)
- 확정된 와이어프레임 기반으로 화면 설계 구체화
- MVP 기능 목록 문서화 및 개발 태스크 분배
- Post-MVP 기능 백로그 정리 (사용자 커스텀 루트 추가 등)

### 📘 0422 · Wed

#### 오늘 한 일 (What I did)

- 팀 전체 와이어프레임 finalize 및 용어 통일 (루트 → 코스, 커밋메세지 → 제목)
- 핵심 기능(러닝 코스 에디터) UX 배치 방향 논의 — 탭 내 진입 vs 대표 메인버튼
- 인프라 담당 역할 배정 및 팀장님께 셋업 방향 가이드 수령
- EC2 환경에서 apt update 및 Docker 설치 완료

#### 배운 것 (What I learned)

- Nginx + Jenkins를 Docker 방식으로 구성하면 직접 설치 방식 대비 환경 분리와 이식성이 좋음
- CI/CD 목표: GitLab develop 브랜치 push → EC2 자동 배포 반영
- 모니터링 스택 개념 입문: Grafana(인프라 시각화 UI), Loki(로그 수집), Prometheus(메트릭 수집)

#### 문제 & 해결 (Problem & Solution)

- 문제: 코스 에디터를 탭 내부에 묻으면 차별점이 안 보임
- 해결: 핵심 기능인 만큼 대표 메인버튼으로 전면 배치하기로 결정
- 잠재적 문제 (팀장님 후기): Jenkins 재배포 시 예전 컨테이너가 그대로 살아있어 최신 버전이 반영 안 되는 이슈 발생했던 사례 있음
- 대응 방향: 컨테이너 교체 순서 및 이미지 버전 관리 주의해서 운영 예정

#### 인사이트 (Insight)

- 핵심 기능일수록 UX 깊숙이 숨기면 안 됨 — 차별점은 보여야 차별점
- 인프라는 "돌아간다"와 "올바른 버전이 돌아간다"가 다른 문제

#### 다음 할 것 (What's Next)

- Docker 기반 Jenkins + Nginx 컨테이너 구성
- GitLab webhook 연동 및 develop 브랜치 자동 배포 파이프라인 구축
- Prometheus / Loki / Grafana 스택 개념 추가 정리

### 📘 0423 · Thu

#### 오늘 한 일 (What I did)
- EC2 UFW 방화벽 포트 설정 (22, 80, 443, 9090)
- Docker + docker-compose로 Jenkins, Nginx, Certbot 컨테이너 구성
- Jenkins 초기 설정 및 GitLab Webhook 연동 (develop push → 자동 빌드 트리거)
- Certbot SSL 인증서 발급 및 Nginx HTTPS 적용 (http → https 리다이렉트)
- 팀 전체 ERD 및 API 명세서 리뷰

#### 배운 것 (What I learned)
- Docker Compose로 여러 컨테이너(Jenkins, Nginx, Certbot)를 한 번에 올리고 관리하는 흐름
- Certbot + Nginx 조합으로 SSL 인증서 발급 및 HTTPS 리다이렉트 적용하는 방법
- 단일 테이블에 여러 상태(status/enum)를 몰아넣으면 특정 상태 조회 시 전체 row를 스캔하게 되어 성능 문제로 이어질 수 있다는 것

#### 문제 & 해결 (Problem & Solution)
- **문제:** 코스 테이블을 단일 테이블로 관리할 경우, editor 임시저장 / 검증 완료 / 기록 저장 / 공유 상태를 enum 하나로 관리하게 되어 특정 상태 조회 시 전체 row 풀스캔 발생 우려
- **해결:** 실제 성능 저하는 수만 건 이상일 때 유의미하다는 팀원 의견 반영, 단일 테이블 통합으로 방향 확정

#### 인사이트 (Insight)
- 상태(enum)가 많아질수록 테이블 설계는 "어떻게 조회할 것인가"를 먼저 생각해야 함 — 쓰기 편한 구조와 읽기 빠른 구조는 다를 수 있음
- CI/CD 파이프라인 한 사이클을 직접 구축해보니 각 컴포넌트(GitLab, Webhook, Jenkins, Nginx)가 어떤 역할로 연결되는지 흐름이 잡힘

#### 다음 할 것 (What's Next)
- 코스 테이블 설계 방향 확정 (분리 여부 및 인덱스 전략)
- Jenkins 파이프라인 스크립트 작성 및 실제 배포 테스트
- ERD 최종 확정 후 API 명세 기반 개발 태스크 분배

### 📘 0424 · Fri

#### 오늘 한 일 (What I did)
- 어제 EC2에서 직접 작업한 내용 GitLab `infra/` 폴더에 소급 커밋 (브랜치 2개)
- docker-compose.yml 정리 — Certbot 제거, Jenkins 외부 포트(9090) 제거, prefix 환경변수 추가
- Nginx default.conf에 `/jenkins` 리버스 프록시 라우팅 추가
- UFW에서 9090 포트 닫기
- `https://k14a103.p.ssafy.io/jenkins` 접속 확인 완료
- GitLab backend Webhook URL HTTPS로 변경 (MR은 팀장 권한 필요)

#### 배운 것 (What I learned)
- Jenkins 외부 포트를 docker-compose에 열어두면 직접 접근이 가능해져 보안 문제가 생길 수 있음 — Nginx 통해서만 접근하도록 포트 닫는 게 맞음
- `JENKINS_OPTS=--prefix=/jenkins` 환경변수를 줘야 Jenkins 자체가 `/jenkins` 경로를 인식함 (안 주면 리소스 경로 꼬임)
- docker-compose를 여러 단위로 나눠서 관리할 수도 있다는 것 — 인프라 규모 커지면 분리 고려 필요

#### 문제 & 해결 (Problem & Solution)
- **문제:** 9090 포트가 외부에 열려 있어 Nginx 우회 직접 접근 가능한 상태였음
- **해결:** docker-compose에서 포트 바인딩 제거 + UFW 9090 닫기로 Nginx 경유만 허용

#### 인사이트 (Insight)
- 인프라는 "돌아가면 됐다"가 아니라 "어디서 어떻게 접근 가능한가"까지 챙겨야 함
- 개념 없이 설정 먼저 건드리면 나중에 더 꼬임 — Docker 강의 먼저 듣고 구조 잡는 게 맞겠다 싶었음

#### 다음 할 것 (What's Next)
- Docker 인프런 강의 수강
- Nginx 리버스 프록시 규칙 우선순위 공부
- 백엔드/프론트 코드 나오면 Jenkins 파이프라인 작업 시작
